# R8/R9 구현 계획과 미결정 정책

검토일: 2026-11-13. 프론트엔드 API 요청서 2차의 R8/R9에 대한 **설계안**이다. 이번 작업에서는 R7만 구현하며 R8/R9 API, 삭제 로직, 관련 스키마 변경은 구현하지 않는다. 아래 권장안은 삭제 정책이나 운영 적용에 대한 최종 승인·확정이 아니다.

첨부 요청서의 “즉시 만료” 등 제안은 참고 자료로 검토했다. 사용자의 안전 규칙에 따라 파괴적인 삭제 방식을 임의로 선택하지 않는다. 운영 Supabase DB·Storage에 접속하지 않았으며 Railway 배포, `.env`·인증키 변경, Flyway V1~V7 변경도 하지 않았다. 근거는 저장소 코드와 스키마이며 실제 운영 데이터·Storage 동작을 확인한 결과가 아니다.

## 1. 현재 구조와 삭제 위험

| 참조 | 현재 삭제 규칙 | 영향 |
| --- | --- | --- |
| `subject → material`, `subject/material → category`, `category → question` | `ON DELETE CASCADE` | 자료/과목 삭제가 문제 삭제까지 이어짐 |
| `question → attempt.question_id` | CASCADE 없음 | 답안이 있으면 문제·자료·과목 물리 삭제가 FK 위반으로 실패 |
| `question → session_question`, `question → wrong_note` | `ON DELETE CASCADE` | 답안이 없어도 세션 문항과 오답 행이 사라짐 |
| `material → material_page/material_file` | `ON DELETE CASCADE` | 원문 텍스트·객체 경로가 함께 사라져 사후 Storage 정리가 어려워짐 |
| `session.category_ids` | FK가 없는 배열 | 과목/단원 물리 삭제 후 존재하지 않는 ID가 남을 수 있음 |

근거: [V1 초기 스키마](../src/main/resources/db/migration/V1__init_schema.sql#L21), [V2 material_page](../src/main/resources/db/migration/V2__add_ai_integration_columns.sql#L55), [V4 material_file](../src/main/resources/db/migration/V4__add_material_file.sql#L3).

따라서 `DELETE FROM material/subject`를 바로 실행하거나 FK에 CASCADE를 추가하는 방식은 채택하지 않는다. 혼합 과목 세션을 통째로 삭제하면 다른 과목의 학습 기록까지 잃는다. FK만 해결하려고 attempt를 선행 삭제하는 것도 기록 삭제 정책을 임의로 결정하는 것이 된다.

## 2. 자연 만료와 사용자 삭제를 구분

현재 자동 정리는 7일 경과 또는 계정의 READY/FAILED 자료 10개 초과 시 원본을 제거하고 `EXPIRED`로 바꾼다. 단원, 요약, 문제, 오답, 답안, `material_page`는 남긴다. 자료 목록·단원 목록은 EXPIRED를 제외하지 않으며 기존 문제도 계속 풀 수 있다. 세션의 부족 문항 추가 생성에서만 EXPIRED 자료를 제외한다.

근거: [기존 만료 정책](슬라이스10_자료_정리.md#L3), [자료 목록 조회](../src/main/java/com/likelion/commute_study_api/material/MaterialRepository.java#L36), [단원 목록 조회](../src/main/java/com/likelion/commute_study_api/study/StudyReadRepository.java#L16), [세션 추가 생성 대상](../src/main/java/com/likelion/commute_study_api/session/service/SessionService.java#L193).

사용자 삭제를 `EXPIRED`로만 표현하거나 모든 EXPIRED 항목을 숨기면 기존 자연 만료 정책까지 바뀐다. **별도 `deleted_at` 표식을 두는 소프트 삭제를 우선 검토**한다. 물리 행과 학습 기록은 보존하고 새 학습 선택·자료/단원 목록에서는 사용자 삭제 항목만 숨기는 안이다. 과목에도 같은 구분이 필요하다. 실제 컬럼·인덱스는 정책 확정 후 당시 최신 Flyway 다음 버전으로 별도 설계한다.

단, 아래 노출 정책은 아직 결정이 필요하다.

- 삭제한 자료/과목의 오답을 목록에서 숨길지, 과거 기록 화면에서 계속 보여줄지.
- 기존 세션의 답안 제출·이어 풀기·문제 해설 조회를 허용할지. 완료 세션의 답안 수·정답률은 삭제 때문에 줄어들지 않게 보존하는 것을 권장한다.
- 보존하는 `material_page` 원문과 질문·해설의 범위 및 보존 기간. “원본 파일 삭제”가 “추출 텍스트까지 삭제”를 뜻하지는 않는다.
- 같은 ID의 반복 DELETE를 204로 처리할지, 숨겨진 리소스로서 404로 처리할지.

## 3. R8: DELETE /api/materials/{id}

목표 계약은 JWT 필수, 본인 자료만 삭제, 성공 204, UPLOADED/PROCESSING 409 `STATE_CONFLICT`, 없거나 남의 자료 404 `NOT_FOUND`다. 상태보다 소유권을 먼저 확인해 타인의 상태를 노출하지 않는다. 기존 [MaterialRepository.owned](../src/main/java/com/likelion/commute_study_api/material/MaterialRepository.java#L46)와 공통 오류 코드를 재사용할 수 있다.

권장 처리 흐름:

1. 짧은 트랜잭션에서 소유권·삭제 여부·상태를 확인하고 사용자 삭제 의도를 저장한다. 상태 조건을 UPDATE에도 넣거나 행을 잠가 retry/worker와 경합을 처리한다.
2. 원본 삭제용 경로와 재시도 의도를 내구적으로 보존한다. DB 트랜잭션 밖에서 Storage를 정리한다.
3. 성공 후 별도 트랜잭션에서 원본 경로를 비우고 정리 완료를 기록한다. 파일 일부 삭제나 DB 저장 실패 시 재시도 가능한 경로와 예약을 남긴다.

기존 [예약/완료 트랜잭션](../src/main/java/com/likelion/commute_study_api/material/MaterialRetentionTransactions.java#L21), [cleanup_pending 조건부 갱신](../src/main/java/com/likelion/commute_study_api/material/MaterialRetentionRepository.java#L39), [Storage 삭제 흐름](../src/main/java/com/likelion/commute_study_api/material/MaterialRetentionService.java#L77)을 재사용·확장할 수 있다. 이미지 자료는 [material_file의 모든 경로](../src/main/java/com/likelion/commute_study_api/material/MaterialRepository.java#L60)를 정리해야 하며 첫 `file_url`만 지우면 나머지가 남는다. Storage는 명시적인 `NoSuchKey`만 이미 삭제된 성공으로 취급하고 일반 404·인증 오류·버킷 없음은 실패로 유지한다([구현](../src/main/java/com/likelion/commute_study_api/material/storage/SupabaseMaterialStorage.java#L58)).

204의 완료 의미는 확정해야 한다. 논리 삭제와 정리 예약 완료에 204를 줄지, 실제 객체 정리까지 성공해야 204를 줄지에 따라 실패 응답과 재시도 동작이 달라진다. 기존 자동 정리는 [cleanup-enabled 기본 false](../src/main/resources/application.yaml#L94)이므로 예약만 저장하고 기존 스케줄러에 의존하면 원본이 정리되지 않을 수 있다. 삭제 요청용 실행·재시도 경로를 명시적으로 설계해야 한다. 기존 서비스의 JVM 동기화만으로는 여러 인스턴스와 API/스케줄러 동시 실행을 모두 직렬화하지 못하므로 내구적 작업 예약·lease도 검토한다.

## 4. R9: PATCH /api/subjects/{id}

목표는 전달한 필드만 수정하며 `examDate: null`은 시험일 제거, 성공은 200 `{id,name,examDate,dDay}`다. 소유권 불일치는 기존 과목 API와 같은 404를 권장한다.

기존 [SubjectRequestDeserializer](../src/main/java/com/likelion/commute_study_api/subject/SubjectRequestDeserializer.java#L19)는 누락한 examDate와 명시적인 null을 모두 Java null로 바꾸므로 POST DTO를 그대로 재사용하면 안 된다. 별도 PATCH DTO/역직렬화에서 `namePresent`, `examDatePresent` 등 존재 여부를 보존한다. SQL `COALESCE`만으로는 명시적 null 삭제를 표현할 수 없다.

| 요청 필드 | 권장 처리 |
| --- | --- |
| name 누락 | 기존 값 유지 |
| name 문자열 | `strip()` 후 기존 Unicode 1~20자 규칙 적용 |
| name null/공백/숫자/배열 등 | POST와 동일한 400 `VALIDATION_ERROR` |
| examDate 누락 | 기존 값 유지 |
| examDate null | DB NULL로 삭제 |
| examDate 문자열 | `YYYY-MM-DD` 형식과 실제 날짜, 0001~9999년을 엄격 검증 |
| examDate 빈 문자열/잘못된 날짜/타입 불일치 | 400 `VALIDATION_ERROR` |

[기존 이름 검증](../src/main/java/com/likelion/commute_study_api/subject/SubjectRequest.java#L10), [엄격한 날짜 파싱](../src/main/java/com/likelion/commute_study_api/subject/SubjectRequestDeserializer.java#L21)을 공통 함수로 공유하는 안을 검토한다. 존재 여부를 판별한 후 전달된 필드만 갱신하고 UPDATE의 WHERE에 과목 ID·사용자 ID·미삭제 조건을 함께 둔다. 동시 PATCH가 서로 생략한 필드를 덮어쓰지 않아야 한다. D-Day는 [기존 SubjectService](../src/main/java/com/likelion/commute_study_api/subject/SubjectService.java#L25)처럼 요청 시점 KST 날짜 기준으로 계산한다. 빈 객체 및 알 수 없는 필드 처리와 시험일이 없는 응답의 null/생략 형식은 문서로 확정한다.

## 5. R9: DELETE /api/subjects/{id}

과목의 소프트 삭제와 그 아래 자료의 원본 정리를 묶어 설계하는 것을 권장한다. subject만 숨기면 Storage 원본이 남고, 하위 자료만 지우면 category.subject_id와 기록 참조가 깨진다. 같은 과목의 모든 정리 대상 경로를 확보하고 재시도 작업을 남긴 뒤 과목·자료의 사용자 삭제 표식을 반영하는 흐름을 검토한다.

처리 중 자료가 하나라도 있으면 과목 삭제를 409로 거절할지, 취소·정리 작업으로 넘길지 확정해야 한다. 부분 과목 삭제를 허용할지도 결정해야 한다. READY 자료라도 단원 문제 생성이 아직 진행 중일 수 있으므로 자료 상태 검사만으로 비동기 작업이 모두 끝났다고 볼 수 없다.

R2는 이미 [과목과 무관한 ACTIVE 조건](../src/main/java/com/likelion/commute_study_api/user/UserService.java#L32)을 사용한다. 마지막 과목 삭제로 온보딩에 돌아가지 않도록 이 조건을 유지한다. 다만 [UserRepository.hasSubject](../src/main/java/com/likelion/commute_study_api/user/UserRepository.java#L57)와 [세션 생성 설정 검사](../src/main/java/com/likelion/commute_study_api/session/service/SessionService.java#L144)는 활성 과목 존재 여부로 맞춰야 한다.

## 7. 권장 검증과 미검증 범위

- JWT 없음/유효하지 않음 401, 타인/없는 ID 동일 404, 타인 자료 상태 비노출.
- 자료 READY/FAILED/EXPIRED 삭제, UPLOADED/PROCESSING 409, 반복 DELETE 계약, retry와 삭제의 동시 요청.
- PDF/PPTX 및 PNG/JPG 여러 장 전체 경로 정리, 일부 삭제 실패, NoSuchKey와 일반 404 구분, Storage 성공 뒤 DB 실패·재시작 후 복구.
- 자연 만료 자료의 기존 노출·풀이 유지와 사용자 삭제 항목 제외를 별개로 검증; 보관 개수 계산·정리 재시도에도 반영.
- 삭제 전후 과거 혼합 과목 세션의 answered/graded/accuracy/feedback 보존, 진행 세션 정책, 과거 해설/오답 접근 정책.
- worker 대상 선택 직후 삭제, AI 응답 도착 직전 삭제, 삭제 과목으로 업로드 경합 시 데이터 재생성·고아 객체 방지.
- PATCH 각 필드의 누락/명시적 null/유효값, 공백·과도한 길이·잘못된 타입·윤년·잘못된 날짜, 동시 부분 갱신, KST 날짜 경계 D-Day.
- 마지막 과목 삭제 뒤 ACTIVE 유지와 hasSubject=false, 새 과목/자료 등록 흐름, 기존 POST/GET 과목 API 호환성.
- 격리 PostgreSQL에서 FK·조건부 UPDATE·마이그레이션을 검증하고 Java 전체 테스트를 실행한다. H2만으로 PostgreSQL 잠금·enum·CASCADE 동작의 운영 동일성을 단정하지 않는다.
