# 슬라이스 16 — 실시간 AI 질문 및 일일 사용량

기준: [Issue #31](https://github.com/Subway-Line-1-Hackathon/commute-study-backend/issues/31), develop `5c5e9c9`, 작업 브랜치 `Feat/#31`.

## API

`POST /api/questions/{id}/ask`: Bearer JWT, JSON 요청, SSE 응답. 빈/공백 message, 잘못된 history role, null history 항목/content는 400 `VALIDATION_ERROR`. history 생략/null은 빈 목록이다. 메시지 원문은 그대로 전달하고 history는 마지막 6개를 시간 순서대로 전달한다. 고정 꼬리질문도 같은 경로를 사용한다.

```json
{"message":"왜 틀렸어?","history":[{"role":"user","content":"개념을 설명해줘"},{"role":"assistant","content":"이 개념은..."}]}
```

본인 문제가 아니거나 없으면 404, 진행 중인 질문이 있으면 409 `STATE_CONFLICT`, 잔여 횟수가 없으면 429 `AI_QUESTION_LIMIT`이다. 서버가 지원하지 않는 문제 생성 요청의 처리 책임은 기존 AI 서버에 있다.

`GET /api/users/me/ai-quota`: Bearer JWT로 현재 KST 날짜의 사용량을 읽는다. 기록이 없으면 0이며 remaining은 음수가 되지 않는다.

```json
{"used":3,"limit":20,"remaining":17}
```

## AI 요청 데이터

`TutorContextRepository`는 question → category → subject 소유권을 확인한다. 단원의 material_id 및 page_start~page_end 범위에 해당하는 material_page만 page 순으로 전달한다. Storage를 조회하지 않으며 EXPIRED 자료도 동작한다.

기존 `TutorAskRequest`의 category, question, history, message 필드만 전송한다. choices JSON은 문자열 목록으로 변환한다. 기존 저장 계약인 MC 숫자 문자열(1~4), OX O/X, 단답 대표 answer를 사용한다. answer가 비어 있으면 accepted_answers 첫 값을 대표값으로 사용한다. 기존 NULL 해설은 AI 필수 문자열 계약에 맞게 빈 문자열로 보낸다.

userAnswer는 attempt.user_id와 session.user_id를 **모두** 현재 사용자로 제한한다. IN_PROGRESS 세션의 응답을 우선하고, 같은 우선순위에서는 answered_at DESC, attempt.id DESC로 선택한다. 진행 중인 세션에 응답이 없으면 가장 최근의 다른 세션 응답, 기록이 없으면 빈 문자열이다. API에 sessionId가 없으므로 실제 화면의 세션과 일치하지 않을 수 있다. 향후 프론트/세션 담당과 sessionId 명시 여부를 합의해야 한다.

## SSE와 오류 처리

Servlet AsyncContext와 전용 Java 21 가상 스레드 executor를 사용한다. 기존 AI-01/02 aiExecutor와 HTTP 요청 스레드를 긴 AI 스트림으로 점유하지 않는다. 사용자별 점유는 concurrent set으로 관리하며 정상 완료·오류·실행 거부·클라이언트 연결 오류·타임아웃에 해제한다. 종료 후 늦게 도착한 콜백과 중복 done은 무시한다.

각 이벤트를 UTF-8 JSON으로 직렬화하고 즉시 flush한다. 응답 헤더는 `Content-Type: text/event-stream`, `Cache-Control: no-cache`, `X-Accel-Buffering: no`다.

```text
event: delta
data: {"text":"스택은"}

event: done
data: {"meta":{"model":"mock","inputTokens":1,"outputTokens":2,"elapsedMs":10,"attempts":1}}

```

첫 이벤트 전 연결/HTTP 오류는 JSON 502 `AI_UNAVAILABLE`, 시간 초과는 JSON 504 `AI_TIMEOUT`이다. 입력 검증/소유권/횟수 오류도 JSON이다. 클라이언트가 Accept: text/event-stream만 보내도 JSON Content-Type을 명시한다.

delta 전송 이후 오류는 HTTP 상태를 바꾸지 않고 SSE error를 보낸다. AI가 명시적으로 error 이벤트를 보내면 첫 이벤트인 경우에도 SSE로 중계하며 원래 code/message를 유지한다. 이미 전달한 delta는 유지한다. 내부 예외/DB 오류의 SQL·인증정보·원문은 사용자에게 전달하지 않는다.

```text
event: error
data: {"error":{"code":"AI_UNAVAILABLE","message":"AI 서버 호출에 실패했습니다."}}

```

기존 `TutorAiClientImpl`을 보완했다. 파싱 및 listener 예외를 삼키지 않고, done/error 없는 EOF와 잘못된 이벤트를 실패로 처리한다. 다중 data 줄과 마지막 빈 줄 없는 종료 이벤트도 처리한다. 첫 terminal 이벤트 이후 읽기를 중단하고 HTTP body를 닫는다. 비정상 응답 본문과 URL을 로그에 남기지 않는다.

기존 `ai.timeout.ai05=15`를 Servlet 비동기 timeout과 AI 클라이언트 전체 읽기 deadline에 재사용한다. HttpRequest timeout만으로 제한되지 않는 스트림 body 읽기도 deadline에서 interrupt/close한다. 첫 글자 2초는 목표이며 코드에서 네트워크/모델 성능을 보장할 수 없다. 로컬 HTTP 테스트는 done을 보류한 상태에서도 delta가 먼저 도착하는 것을 검증한다. Railway 프록시 및 실제 모델의 첫 글자/전체 지연은 배포 후 별도 측정해야 한다.

## 사용량 원자성, 날짜 및 전송 경계

기존 ai_question_usage(user_id,date) PK와 `ai.question-daily-limit`를 사용한다. 새 마이그레이션은 없다. 성공한 done을 처리하는 시점의 **KST 날짜**를 사용한다. 자정을 넘긴 스트림은 완료한 날짜에 차감하며 시작 전과 완료 시 모두 한도를 확인한다.

단일 DB 트랜잭션에서 다음 두 문장으로 행 생성과 조건부 증가를 수행한다. Java에서 조회한 숫자를 +1 해서 저장하지 않는다.

```sql
INSERT INTO public.ai_question_usage(user_id,date,count)
VALUES (?, ?, 0) ON CONFLICT DO NOTHING;

UPDATE public.ai_question_usage SET count=count+1
WHERE user_id=? AND date=? AND count<?;
```

UPDATE 영향 행 수가 정확히 1일 때만 성공한다. 신규 행 경합은 PK/ON CONFLICT, 기존 행 증가 경합은 DB UPDATE 행 잠금과 조건 재평가로 보호한다. PostgreSQL과 H2 PostgreSQL 모드 모두 지원하는 형태의 2문장 transactional upsert다. 35개 동시 증가가 정확히 20개만 성공하는 격리 DB 테스트가 있다.

DB 차감 트랜잭션이 커밋된 뒤 done을 전송한다. DB 저장 실패 시 정상 done을 보내지 않는다. done 전송에서 확인된 I/O 실패가 발생하면 차감한 **원래 날짜**에서 원자적으로 1회 보상한다. delta 중단/AI 실패/timeout은 차감하지 않는다.

**분산 시스템 경계:** DB 커밋과 브라우저 수신은 하나의 원자적 트랜잭션으로 묶을 수 없다. 클라이언트가 끊겨도 서버가 아직 감지하지 못한 경우, 커밋 직후 프로세스 종료, 보상 DB 작업까지 실패한 경우에는 사용량이 남을 수 있다. 보상 실패는 사용자 ID·날짜만 기록한다. 브라우저의 실제 수신까지 exactly-once 보장이 필요하면 요청 ID, 영속적인 처리/보상 기록, 클라이언트 ACK 계약을 별도 설계해야 한다. 이번 변경은 현재 스키마 안에서 감지된 연결 실패를 보상한다.

사용자별 한 번에 1개 제한은 현재 Railway 단일 인스턴스 전제다. 여러 인스턴스에서도 DB 횟수 상한은 유지되지만 사용자별 동시 질문 잠금은 공유되지 않는다. 확장 전 분산 lease/lock 및 장애 복구 계약을 추가해야 한다.

## Swagger / curl / fetch 검증

Swagger에서 Google 로그인 또는 Authorize 후 두 경로를 확인한다. 실제 과금/운영 DB 대신 격리 개발 DB와 AI Mock을 사용한다. 사용량 GET → 질문 POST → delta → done → 사용량 GET 순서로 확인한다. 20회 사용 이후 요청이 429인지와 실패 후 사용량 유지/재시도를 확인한다. 운영 계정의 횟수를 테스트 목적으로 채우지 않는다.

Swagger UI는 SSE를 묶어서 표시할 수 있다. PowerShell에서 다음처럼 `curl.exe -N`으로 버퍼링 없이 확인한다. JWT는 화면/로그에 출력하지 않고 TEST_JWT 환경변수에 별도로 주입한다. verbose/trace 옵션은 사용하지 않는다. `ask.json`에는 질문 JSON만 저장한다.

```powershell
curl.exe -sS -H "Authorization: Bearer $env:TEST_JWT" "$env:TEST_BASE_URL/api/users/me/ai-quota"
curl.exe -sS -N -H "Authorization: Bearer $env:TEST_JWT" -H "Content-Type: application/json" -H "Accept: text/event-stream" --data-binary "@ask.json" "$env:TEST_BASE_URL/api/questions/123/ask"
```

Authorization 헤더가 필요하므로 브라우저는 EventSource 대신 fetch를 사용한다. 아래는 token을 인자로 받아 로그에 출력하지 않는 예시다. error 이벤트 이후 partial text를 지우지 않고 재시도 버튼을 표시한다. HTTP JSON 오류도 SSE 파싱 전에 구분한다.

```javascript
async function ask(baseUrl, id, token, message, history, onEvent, signal) {
  const response = await fetch(`${baseUrl}/api/questions/${id}/ask`, {
    method: 'POST', signal,
    headers: { Authorization: `Bearer ${token}`, 'Content-Type': 'application/json', Accept: 'text/event-stream' },
    body: JSON.stringify({ message, history })
  });
  if (!response.ok) throw await response.json();
  const reader = response.body.pipeThrough(new TextDecoderStream()).getReader();
  let buffer = '';
  try {
    while (true) {
      const { value, done } = await reader.read();
      if (done) break;
      buffer += value;
      let end;
      while ((end = buffer.indexOf('\n\n')) >= 0) {
        const frame = buffer.slice(0, end); buffer = buffer.slice(end + 2);
        const lines = frame.split('\n');
        const event = lines.find(line => line.startsWith('event:'))?.slice(6).trim();
        const data = lines.filter(line => line.startsWith('data:')).map(line => line.slice(5).trimStart()).join('\n');
        if (event && data) onEvent(event, JSON.parse(data));
      }
    }
  } finally { reader.releaseLock(); }
}
```

서버는 LF 프레임을 보낸다. 프론트는 AbortController로 중단할 수 있으며, done 수신 후 quota를 다시 읽는다. done/error 없이 EOF가 오면 프론트에서도 완료로 표시하지 않고 연결 오류로 처리한다. 네트워크 버퍼가 이미 수신한 done까지 취소하는 것은 서버에서 보장할 수 없다.

## 테스트와 배포 전 확인

AI mock listener + 격리 H2 DB + 실제 임베디드 Tomcat HTTP로 API/동시성/전송 순서를 검증한다. 별도 loopback HTTP 서버로 실제 TutorAiClient SSE 파서, 잘못된 이벤트, EOF, HTTP 401, 멈춘 body의 전체 deadline을 검증한다. 운영 Supabase/Storage, Railway 및 OpenAI를 호출하지 않았다.

실행: JDK 21 `./gradlew test --no-daemon`, `node --test scripts/swagger-auth.test.cjs`.

최종 결과(2026-11-08 KST): **Java 전체 434 성공 / 0 실패 / 0 오류 / 0 스킵**, **JavaScript 10 성공 / 0 실패 / 0 스킵**. Tutor 통합 테스트 22개, AI-05 클라이언트 테스트 7개를 포함한다. `git diff --check` 통과. 브랜치는 `Feat/#31`, 수정 3개·신규 10개이며 staged 변경은 없다.

운영 배포 전 확인:

1. 기존 AI_SERVER_URL, AI_INTERNAL_KEY와 DB 연결을 확인한다. 비밀 값은 코드/문서에 기록하지 않는다. 새 필수 환경변수는 없다. 일일 제한은 ai.question-daily-limit(기본 20), AI timeout은 ai.timeout.ai05(기본 15초)다.
2. Railway Java 21 및 replica 1개를 확인한다. 가상 스레드는 AI-01/02 executor와 별개다.
3. 격리된 실제 PostgreSQL에서 quota 경합과 실행 계획을 확인한다. H2 통과가 실제 PostgreSQL 부하 검증을 대신하지 않는다.
4. AI 담당과 AI Mock/실제 모델 배포 상태 및 첫 글자 2초/전체 응답 목표를 확인한다. Railway 프록시가 이벤트를 묶지 않는지 fetch/curl로 측정한다.
5. 자정 완료일 과금, userAnswer 선택 기준, "자료에 없는 내용"도 done이면 차감하는 정책, 전송/과금의 분산 경계를 공유한다.

기존 로그인/JWT/설정/과목/자료/AI-01/02/진도/세션/채점/오답 구현 및 V1~V5는 변경하지 않았다. `.env`와 운영 설정도 변경하지 않았다. 슬라이스 17~19는 구현하지 않았다. Commit/Push/PR/Merge는 실행하지 않았다.
