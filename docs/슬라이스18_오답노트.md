# 슬라이스 18 — 과목별 오답노트 조회

기준: [Issue #34](https://github.com/Subway-Line-1-Hackathon/commute-study-backend/issues/34), 최신 develop `efc8ce6`, 작업 브랜치 `Feat/#34`. 기존 작업 트리는 깨끗했으며 미완성 파일을 삭제하거나 덮어쓰지 않았다.

## API

JWT Bearer 인증이 필요한 읽기 전용 API다.

- 전체: `GET /api/subjects/8/wrong-notes`
- 단원 필터: `GET /api/subjects/8/wrong-notes?categoryId=11`

```json
{
  "items": [
    {"questionId":176,"categoryId":11,"stem":"스택의 특징은?","wrongCount":3,"status":"OPEN","lastWrongAt":"2026-11-08T13:30:00Z"},
    {"questionId":177,"categoryId":11,"stem":"큐의 특징은?","wrongCount":2,"status":"RESOLVED","lastWrongAt":"2026-11-07T15:20:00Z"}
  ]
}
```

오답이 없으면 `{"items":[]}`를 HTTP 200으로 반환한다. categoryId를 생략하면 전체 목록이며, 제공한 값이 빈 문자열·숫자 형식 오류·오버플로·0·음수이면 400 VALIDATION_ERROR다. 없는 과목/단원, 남의 과목/단원, 요청 과목과 다른 과목의 단원은 같은 404 NOT_FOUND 계약으로 응답한다. JWT가 없으면 401이다.

lastWrongAt은 저장된 timestamptz를 ISO 8601 offset 형식으로 반환한다. 출력 offset이 달라도 같은 Instant를 뜻한다. 질문 정답·해설·다른 사용자 응답은 추가로 반환하지 않는다. 자료가 EXPIRED여도 보존된 문제와 오답은 조회할 수 있다.

## SQL, 정렬, 상한 및 필터

`wrong_note → question → category → subject`를 조인하여 stem과 categoryId를 가져온다. subject.id, subject.user_id, wrong_note.user_id 조건을 모두 적용한다. CurrentUser.authenticatedId로 검증된 JWT UUID만 추출하고 SubjectRepository.requireOwned로 과목 소유권을 확인한다. 단원 필터가 있으면 해당 단원이 요청 과목과 사용자에 속하는지도 확인한다.

목록 SQL은 과목 전체에서 상태별 순위를 계산한다.

```sql
ROW_NUMBER() OVER (
  PARTITION BY wn.status
  ORDER BY wn.last_wrong_at DESC, wn.question_id DESC
)
```

1. 사용자·과목 조건으로 먼저 범위를 제한한다.
2. OPEN은 WrongNoteProperties.maxOpen(기본 100), RESOLVED는 maxResolved(기본 50) 이내만 선택한다.
3. **상한 적용 후** categoryId를 필터링한다.
4. 두 상태를 합쳐 last_wrong_at DESC, question_id DESC로 정렬한다. OPEN 우선 정렬이 아니다.

기본 최대 150개이며 설정 변경도 적용한다. categoryId 필터를 걸어도 단원별로 상한을 새로 채우지 않는다. 해당 단원에 오래된 오답이 있어도 과목별 상한 밖에만 있으면 빈 목록일 수 있다. 이는 기존 SessionRepository.wrongListed가 과목별 OPEN 상한을 먼저 적용하는 정책과 맞춘 것이다.

기존 재풀이 SQL의 ROW_NUMBER에는 동일 시각 보조 정렬이 없었다. 화면과 재풀이 대상이 상한 경계에서 달라지지 않도록 **question_id DESC 한 항목만 추가**했다. 문제 선택·세션 저장·채점 정책은 변경하지 않았다.

초과 행을 DELETE하거나 상태를 변경하지 않는다. 학습 기록과 정답률 집계는 그대로 유지한다. 과목 검증 1회, 목록 1회 SELECT이며 필터가 있을 때 단원 검증 1회가 추가된다. 서비스는 @Transactional(readOnly=true)이며 사용자 행 생성·상태 변경·AI 호출은 없다.

## 기존 상태 전환과 재풀이

기존 AttemptRepository.recordWrong은 최초 오답을 OPEN으로 만들고, 반복 오답은 wrong_count를 증가시키며 RESOLVED도 OPEN으로 되돌린다. last_wrong_at은 GREATEST로 최근 시각을 유지한다. resolveWrong은 OPEN을 RESOLVED로 바꾸며 기록이나 횟수를 삭제하지 않는다. 이번 조회 API는 저장된 결과를 그대로 읽는다.

기존 재풀이 API를 사용하며 별도 엔드포인트는 없다. 이슈의 wrong_notes 표기 대신 실제 SessionSource JSON 계약인 **wrongNotes**를 사용한다.

```json
{
  "source":"wrongNotes",
  "categoryIds":[11],
  "questionTypes":["OX","MC","SHORT"],
  "difficulty":2
}
```

`POST /api/sessions`로 생성하고 기존 세션 시작 → 답안 저장 흐름을 따른다. categoryIds 생략 시 사용자 전체 과목에서, 지정 시 해당 단원의 목록 상한 내 OPEN 후보에서 선택한다. 실제 세션 문제는 기존 유형·난이도·통학시간 정책에 의해 더 적을 수 있다. RESOLVED는 재풀이 후보에서 제외한다.

### 확인된 기존 동작 차이 — 후속 수정 필요

현재 SessionProgressRepository는 **session.category_ids IS NULL**을 오답노트 재풀이 여부로 해석한다. SessionService/SessionWriter는 전달받은 categoryIds를 그대로 저장한다.

- categoryIds를 생략한 wrongNotes 세션은 NULL로 저장되어, 정답 시 기존 resolveWrong이 호출된다.
- categoryIds를 지정한 wrongNotes 세션은 목록을 정상 필터링하지만 배열을 저장하므로 일반 세션으로 인식된다. **정답이어도 자동 RESOLVED 전환이 되지 않는 기존 차이가 있다.**
- 일반 학습 세션에서 정답을 맞히는 경우에도 기존 정책은 해결 상태를 바꾸지 않는다. 따라서 “어떤 방식으로든 한 번 맞히면 해결”과는 다르다.

사용자가 요청한 조회 전용 범위와 기존 상태 전환 유지 지침에 따라 이 동작을 임의로 변경하지 않았다. 필터가 있는 wrongNotes도 재풀이 출처를 보존하도록 저장 계약을 보완할지 세션 담당과 결정해야 한다. 현재 저장되는 categoryIds를 명시적으로 확인하는 회귀 테스트를 추가했다. 목록 API 자체는 실제 DB 상태와 일치하며 해결 상태를 추정해서 덮어쓰지 않는다.

## Swagger 수동 검증

1. Swagger에서 Google 로그인 또는 Bearer Authorize를 설정한다.
2. 실제 본인 과목 ID로 GET /api/subjects/{id}/wrong-notes를 Execute한다. Example Value는 가상 예시이며 Server Response가 실제 데이터다.
3. categoryId를 넣어 해당 단원만 보이는지 확인한다. 상한은 과목 전체 기준임을 유의한다.
4. 오답 없는 과목/단원은 items=[], 잘못된 categoryId는 400, 없는/남의 과목 또는 다른 과목 단원은 404인지 확인한다.
5. 로그아웃 후 401을 확인한다.
6. 별도 테스트 환경에서 source=wrongNotes로 기존 재풀이 흐름을 확인한다. 자동 해결 상태 검증 시 위의 categoryIds 저장 문제를 구분한다. 운영 DB에 시드/강제 상태 변경을 실행하지 않는다.

## 테스트와 한계

격리 H2 DB에서 조회 SQL, 기본 100/50 경계, 총 150개 상한, 초과 행 보존, 설정 변경, 동일 시각 정렬, 단원 필터 순서, 사용자/과목 격리, 빈 목록, JWT·입력 오류, EXPIRED 조회, 읽기 전후 데이터 불변성, 기존 resolveWrong의 DB 변경 후 조회 반영을 검증한다. 동일 시각·상한 경계에서도 기존 SessionRepository.findCandidates의 wrongListed와 목록 OPEN 결과가 일치하는지 실제 SQL로 비교한다.

기존 AttemptService/SessionService/SessionController 테스트도 전체 실행하여 중복 응답, 오답 기록 호출, 재풀이 해결 호출, 일반 정답 비해결 및 wrongNotes JSON 계약을 검증한다. PostgreSQL 전용 recordWrong ON CONFLICT UPDATE의 실제 DB 실행은 H2 통합 테스트에서 대체해 검증했다고 주장하지 않는다. 기존 SQL을 검토했으며 운영 PostgreSQL에는 접근하지 않았다.

실행: JDK 21 `./gradlew test --no-daemon`, `node --test scripts/swagger-auth.test.cjs`.

최종 결과(2026-11-08 KST): **Java 전체 496 성공 / 0 실패 / 0 오류 / 0 스킵**, **JavaScript 10 성공 / 0 실패 / 0 스킵**. `git diff --check` 통과. 작업 브랜치는 `Feat/#34`, 수정 3개·신규 6개이며 staged 변경은 없다.

V1~V5 변경 및 신규 마이그레이션은 없다. .env, 운영 DB/Storage/Railway 설정은 변경하지 않았다. 새 저장/채점 API, 슬라이스 19 인증 리팩터링은 포함하지 않는다. Commit/Push/PR/Merge는 실행하지 않았다.
