# 슬라이스 7: 과목 등록·목록·D-Day

## API

두 API 모두 기존 Supabase Bearer JWT 인증을 사용한다.

```http
POST /api/subjects
Authorization: Bearer <Supabase access token>
Content-Type: application/json

{"name":"선형대수","examDate":"2026-12-15"}
```

HTTP 201 응답: `{"subjectId":1}`. ID는 DB가 생성한다.
시험일은 생략하거나 NULL로 보낼 수 있다. 과거 시험일도 허용한다.
과목명 앞뒤 공백은 제거하고, 공백만 있는 이름·누락·NULL을 거절한다.
이름은 Unicode code point 기준 1~20자이며, 중복 이름과 과목 개수에는 추가 제한이 없다.
시험일은 4자리 연도의 `YYYY-MM-DD` 형식과 실제 존재하는 날짜를 검사한다.
잘못된 값이나 JSON 타입은 기존 공통 형식의 HTTP 400 `VALIDATION_ERROR`다.
DB 저장 실패는 공통 HTTP 500 `INTERNAL_ERROR`로 반환하고 트랜잭션을 롤백한다.

`GET /api/subjects` 응답 예시(2026-11-07 KST 기준):

```json
{
  "subjects": [
    {"id":1,"name":"선형대수","examDate":"2026-12-15","dDay":38},
    {"id":2,"name":"프로그래밍"}
  ]
}
```

과목이 없으면 `{"subjects":[]}`이다. 목록은 인증된 사용자 과목만 ID 오름차순으로 반환한다.
기존 명세서에 정렬 기준이 없어, 생성 ID 기준의 일관된 등록 순서를 선택했다.
날짜가 없으면 `examDate`, `dDay` 모두 생략한다. 과거 시험일은 `examDate`만 반환한다.

## D-Day

`subjectClock`을 주입하고 `clock.withZone(Asia/Seoul)`로 오늘 날짜를 계산한다.
따라서 Railway의 기본 시간대가 UTC여도 KST 자정을 기준으로 날짜가 바뀐다.
목록 요청마다 오늘 날짜를 한 번 구하고 `ChronoUnit.DAYS.between(today, examDate)`를 사용한다.
시험 당일은 0, 미래 날짜는 양수이며, 지난 날짜의 dDay는 생략한다.
테스트에서는 Clock을 고정하고 UTC 14:59:59 → 15:00:00(KST 자정) 경계를 확인한다.

## 사용자·소유권과 트랜잭션

생성·목록 모두 기존 `CurrentUser.ensureUser(jwt)`를 호출한다.
생성은 사용자 자동 생성과 과목 INSERT를 하나의 트랜잭션으로 묶는다.
닉네임이 없는 신규 사용자도 등록할 수 있으며, 실패하면 자동 생성도 롤백한다.
요청에 임의의 `userId`를 넣어도 소유자로 사용하지 않고 JWT sub만 사용한다.
생성 ID는 `GeneratedKeyHolder`에 반환 컬럼 `id`를 지정해 안전하게 읽는다.

다음 슬라이스의 서비스에서 재사용:

```java
UUID userId = currentUser.ensureUser(jwt);
subjectRepository.requireOwned(subjectId, userId);
```

`SubjectRepository`는 `create`, `findAllByUserId`, `isOwnedBy`, `requireOwned`를 제공한다.
소유권 쿼리는 `id`와 `user_id`를 함께 검사한다.
`requireOwned`는 없는 과목과 타인 과목 모두 `ApiException(NOT_FOUND)`를 던져
기존 GlobalExceptionHandler에서 동일한 HTTP 404가 되도록 한다.
과목 상세·수정·삭제 엔드포인트는 추가하지 않았다.

## 기존 상태 연동과 테스트

Java 21 전체 테스트 135개와 Swagger 인증 JavaScript 테스트 10개가 통과했다.

기존 UserService는 변경하지 않았다. 과목 등록 후 기존 조회 쿼리에 의해
`hasSubject=true`가 반영된다. 닉네임·통학 설정도 있으면 ACTIVE,
하나라도 빠져 있으면 AUTHENTICATED다.
설정 저장 → AUTHENTICATED → 과목 등록 → ACTIVE 흐름을 HTTP 통합 테스트로 검증한다.

격리된 H2 PostgreSQL 모드에서 생성 ID·UUID 소유자·목록 격리·입력 검증·선택 필드 생략,
실패 시 롤백·소유권 404 에러·실제 서명된 만료 토큰 거부를 확인한다.
기존 사용자·설정·닉네임 API와 Swagger 인증 회귀 테스트도 유지한다.

```powershell
$env:JAVA_HOME='C:\Program Files\Java\jdk-21.0.12.1'
.\gradlew.bat test --no-daemon
node --test scripts/swagger-auth.test.cjs
```

## Swagger 확인 순서

1. 서버 실행 후 `/swagger-ui/index.html`에서 기존 Google 로그인 버튼으로 로그인한다.
2. `GET /api/subjects`로 본인 목록을 확인한다.
3. 설정 PUT으로 닉네임·시간을 저장하고 `/api/users/me` 상태를 확인한다.
4. 과목 POST 예시를 실행해 HTTP 201과 subjectId를 확인한다.
5. 과목 GET에서 목록·시험일까지의 D-Day를 확인한다.
6. `/api/users/me`의 `hasSubject=true`, `status=ACTIVE` 전환을 확인한다.
7. 시험일 없는 과목, 과거 시험일, 잘못된 날짜를 각각 요청해 필드 생략과 400을 확인한다.

실제 Google 계정 로그인 및 Supabase PostgreSQL의 generated key/FK 동작은 별도 테스트
계정에서 최종 확인해야 한다. 이번 자동 테스트는 운영 DB에 접속하거나 쓰지 않는다.
기존 마이그레이션·`.env`·Railway 설정은 변경하지 않았다.
