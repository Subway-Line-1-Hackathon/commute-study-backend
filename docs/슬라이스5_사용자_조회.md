# 슬라이스 5: 사용자 자동 생성과 내 정보 조회

`GET /api/users/me`는 Spring Security가 검증한 Supabase JWT의 `sub` UUID로
사용자를 식별하고, 사용자 행이 없으면 생성한 뒤 현재 설정 상태를 반환한다.
Google 프로필 이름은 저장하거나 반환하지 않는다.

## API 사용

```http
GET /api/users/me
Authorization: Bearer <Supabase access token>
```

처음 호출한 사용자:

```json
{
  "userId": "11111111-1111-1111-1111-111111111111",
  "nickname": null,
  "status": "AUTHENTICATED",
  "hasSubject": false
}
```

설정이 완료된 사용자:

```json
{
  "userId": "11111111-1111-1111-1111-111111111111",
  "nickname": "동현",
  "status": "ACTIVE",
  "hasSubject": true,
  "settings": {
    "oneWayMin": 50,
    "fromStation": "수원역",
    "toStation": "서울역",
    "studyMin": 50,
    "mode": "CURRICULUM"
  }
}
```

- 닉네임이 NULL/빈 문자열/공백이 아니고, 통학 설정과 본인 과목이 모두 있어야 `ACTIVE`다.
- 하나라도 미완료이면 `AUTHENTICATED`다. 상태는 저장하지 않고 조회 시 계산한다.
- 통학 설정이 없으면 `settings` 필드 자체를 생략한다. 선택값인 역 이름은 NULL일 수 있다.
- `studyMin = oneWayMin`이며 `StudyMode.of`와 `study.curriculum-min-minutes` 설정으로 모드를 계산한다.
- 토큰 누락·만료 시 기존 Security 필터가 401을 반환한다.

## 다음 슬라이스에서 재사용

`CurrentUser`를 생성자로 주입하고, 인증된 `@AuthenticationPrincipal Jwt jwt`를 전달한다.

```java
UUID userId = currentUser.ensureUser(jwt);
```

이 메서드가 반환되면 `app_user` 행의 존재가 보장된다. 인증 토큰 검증은 기존 Spring Security가 담당한다.
직접 만든 JWT나 검증하지 않은 토큰을 전달하지 않는다.
슬라이스 6의 설정 저장, 슬라이스 7의 과목 등록 서비스에서 같은 방식으로 사용한다.
외래 키를 사용하는 쓰기 작업과 묶으려면 호출 서비스에 `@Transactional`을 붙인다.
자동 생성 INSERT가 있으므로 `readOnly=true` 트랜잭션에서 호출하지 않는다.

`UserRepository.createIfAbsent`는 `INSERT ... ON CONFLICT DO NOTHING`을 사용한다.
기존 닉네임과 생성 시각을 덮어쓰지 않으며 PK로 중복을 방지한다.
`UserService.getMe`는 생성과 조회를 하나의 트랜잭션으로 묶는다.
사용자 조회 SQL은 닉네임·통학 설정·본인 과목 유무를 한 번에 읽는다.

기존 `/api/auth/me`, `/api/users/me/nickname` GET·PUT은 유지한다.
`/api/auth/me`에만 OpenAPI deprecated 표시를 추가했다.
설정 저장·과목 CRUD API는 이번 범위에 포함하지 않는다.

## 실제 DB 확인

2026-11-07 로컬 설정의 Supabase DB에 읽기 전용으로 접속해 확인했다.

- `flyway_schema_history`: V1, V2, V3 모두 `success=true`
- `information_schema.columns`: `public.app_user.nickname`의 `is_nullable=YES`
- 기존 마이그레이션과 운영 데이터는 변경하지 않았다.

자동 테스트는 로컬 `.env`를 로드하지 않고 H2 PostgreSQL 모드의 격리된 DB를 사용한다.
신규 사용자 생성, 반복 요청 시 닉네임/생성 시각 보존, 6개 동시 요청, 상태 조합,
사용자별 데이터 격리, 실제 서명된 만료 토큰 거부, 기존 조회 API를 검증한다.
테스트 스키마는 관련 세 테이블만 포함하며 Supabase `auth.users` FK는 포함하지 않는다.
기존 닉네임 PUT의 PostgreSQL upsert 문법은 H2가 지원하지 않으므로
기존 MockMvc·JdbcTemplate mock 회귀 테스트로 HTTP 계약을 검증한다.
H2의 동시 요청 테스트가 PostgreSQL의 잠금 동작 검증을 대체하지는 않는다.

```powershell
$env:JAVA_HOME='C:\Program Files\Java\jdk-21.0.12.1'
.\gradlew.bat test --no-daemon
node --test scripts/swagger-auth.test.cjs
```

## Swagger 및 실제 계정 확인

1. 서버 실행 후 `/swagger-ui/index.html`에서 기존 Google 로그인 버튼으로 로그인한다.
   또는 Authorize에 Supabase access token을 입력한다.
2. `GET /api/users/me`를 실행한다. 신규 계정은 `AUTHENTICATED`, `nickname: null`, `hasSubject: false`가 반환된다.
3. DB에서 같은 UUID의 `app_user` 행이 한 개이며 닉네임이 NULL인지 확인한다.
4. 반복 호출 후 사용자 수와 `created_at`이 그대로인지 확인한다.
5. 기존 닉네임 PUT·GET과 `/api/auth/me`가 동작하는지 확인한다.
6. 통학 설정·과목이 있는 테스트 계정으로 `ACTIVE`와 settings를 확인한다.
   신규 계정의 전체 전환은 이후 슬라이스 6·7 API가 준비되면 확인한다.

실제 Google 로그인, Supabase `auth.users` FK, PostgreSQL 동시 요청,
기존 닉네임 upsert 및 `AUTHENTICATED` → `ACTIVE` 전환은 별도 테스트 계정/격리된
PostgreSQL 환경에서 추가 확인해야 한다. 이번 작업에서는 운영 DB 쓰기 테스트를 실행하지 않았다.
