# 슬라이스 10 — 자료 만료 및 Storage 정리

## 정책과 구현

- `READY`, `FAILED`만 정리한다. `expires_at <= 현재 시각`이면 만료 대상이며, 값이 없는 기존 자료는 `created_at + material.retention-days`(7일)를 사용한다.
- 계정의 모든 과목에서 `READY`·`FAILED`를 합산하고, 10개 초과분을 `created_at, id` 오름차순으로 정리한다. 기간 만료 후 다시 계산하므로 불필요하게 추가 자료를 지우지 않는다. `UPLOADED`·`PROCESSING`은 제외한다.
- 업로드 및 READY/FAILED 전환의 **트랜잭션 커밋 후** 비동기로 정리한다. 매일 **03:00 Asia/Seoul**에도 실행한다. 실패하거나 실행 큐가 가득 찬 경우 다음 정기 실행에서 다시 시도한다.
- 짧은 DB 트랜잭션에서 `cleanup_pending=true`로 예약하고 상태·소유권을 재확인한다. 예약된 자료는 retry할 수 없다. 트랜잭션 종료 후 PDF/PPTX 원본 또는 `material_file`의 PNG 전체 페이지(최대 20장)를 Storage에서 삭제한다.
- 모든 삭제가 성공한 경우에만 별도 트랜잭션에서 `EXPIRED`로 변경하고 `material.file_url` 및 PNG `material_file.file_url`을 빈 문자열로 바꾼다. NOT NULL 제약을 유지하며 파일 행도 보존한다.
- 삭제 실패, 일부 페이지만 삭제, 삭제 후 DB 저장 실패 모두 상태·경로·예약을 남긴다. 재시작 후에도 예약을 읽고 같은 경로를 다시 삭제한다. Storage가 HTTP 400/404와 명시적 `NoSuchKey`를 반환하면 이미 없는 객체로 처리한다. 버킷 없음·권한 오류·일반 404·응답 파싱 오류는 성공으로 간주하지 않는다. 관련 계약: [Supabase Storage 오류 코드](https://supabase.com/docs/guides/storage/debugging/error-codes).
- 단원, 요약, 문제, 오답, 답안, `material_page`는 수정하거나 삭제하지 않는다. AI 문제 생성·학습 세션 로직도 변경하지 않는다.
- `EXPIRED` retry는 기존 조건부 상태 전환을 통해 HTTP 409 `STATE_CONFLICT`를 반환한다. 부분 삭제 중인 FAILED도 409이며, 정리 예약이 없는 유효한 FAILED는 기존 인증·소유권 검증 후 재시도할 수 있다.

## 고착 복구와 동시 실행

`PROCESSING` 전환 시 DB의 현재 시각을 `processing_started_at`에 기록한다. 업로드 시각으로 판단하지 않는다. 1분마다 시작한 지 10분 이상인 작업을 조건부 UPDATE로 FAILED로 복구한다. 매일 정리에서도 먼저 복구한다.

매 시도에 UUID `processing_token`을 부여한다. READY/FAILED 저장은 해당 토큰과 PROCESSING 상태가 일치할 때만 가능하다. 복구 후 새 retry가 시작되어도 이전 AI 응답이 새 상태를 덮어쓰지 못한다. 프로세서의 중복 방지도 자료 ID가 아니라 시도 토큰별로 적용한다.

현재 Railway **단일 인스턴스** 전제에서 정리 서비스의 동기화 및 단일 실행 스레드로 중복 정리를 직렬화한다. DB 예약과 조건부 UPDATE로 retry와 정리의 경합을 방어한다. Storage HTTP 동안 DB 트랜잭션을 유지하지 않는다. 여러 인스턴스로 확장하기 전에는 계정별 분산 락/lease를 도입해야 한다. 특히 계정별 10개 초과분 선정은 JVM 밖까지 직렬화되지 않는다.

## V5 배포

`V5__add_material_lifecycle_tracking.sql`을 새로 추가했다. V1~V4는 변경하지 않았다.

추가 항목: `processing_started_at`(timestamp with time zone), `processing_token`(UUID), `cleanup_pending`(boolean, 기본 false), 상태/시작 시각 인덱스.

기존 PROCESSING 행에는 마이그레이션 시각을 시작 시각으로 기록하여 최소 10분의 유예 시간을 준다. 기존 업로드 시각은 바꾸지 않는다. 오래된 프로세스에는 토큰 검증이 없으므로 **구버전 worker를 정지한 뒤 V5와 새 코드를 배포**한다. 운영에 직접 적용하지 않았으며, 개발 중에도 공유 DB를 대상으로 앱을 실행하지 않았다.

이 프로젝트는 앱 시작 시 Flyway가 실행될 수 있다. 공유 DB에 연결한 로컬 `bootRun`으로 검증하지 않는다. 운영 적용 담당자가 V5 번호 충돌 여부, 백업, DDL 잠금 영향과 배포 순서를 검토한 뒤 승인된 배포 절차로 적용한다. 실패 시 새 컬럼을 수동 삭제하거나 V1~V4 체크섬을 변경하지 않는다.

## Railway 설정 및 배포 전 확인

| 환경변수 | 설정 |
| --- | --- |
| `MATERIAL_CLEANUP_ENABLED` | 기본 `false`. 운영 검증 후 단일 인스턴스에만 `true` |
| `SUPABASE_URL` | 기존 운영 Supabase URL |
| `SUPABASE_STORAGE_BUCKET` | 기존 private bucket |
| `SUPABASE_STORAGE_KEY` | 기존 서버 전용 service_role JWT 또는 sb_secret 키, 삭제 권한 필요 |
| `SUPABASE_HOST` | 기존 AI 파일 다운로드 허용 호스트와 일치 |

기존 DB/Flyway/AI 연결 환경변수도 그대로 필요하다. 새로 필요한 활성화 변수는 `MATERIAL_CLEANUP_ENABLED` 하나다. 이 스위치는 정기 정리·커밋 후 정리·고착 복구를 모두 제어한다. 기존 AI 요청 자체의 타임아웃 처리는 유지한다. 로컬은 기본 비활성화이며 `.env`는 변경하지 않았다.

배포 전 확인 사항:

1. V5를 다른 팀 작업과 함께 검토하고 구버전 worker 종료 및 Railway replica 1개를 확인한다.
2. 별도 테스트 Supabase 프로젝트에서 실제 PostgreSQL 마이그레이션과 Storage의 없는 객체 응답 계약 및 삭제 권한을 확인한다. 운영 객체로 삭제 테스트하지 않는다.
3. 보관 정책(READY/FAILED 합산 10개), 부분 삭제 중 retry 차단, 최초 활성화 시 기존 오래된 원본이 정리되는 점을 확인한다.
4. V5 적용 및 새 코드 배포 후 활성화하고 `expired`, `failed`, `recovered` 로그를 관찰한다. 로그에는 원본 경로·Signed URL·토큰·키·외부 응답 본문을 출력하지 않는다.
5. 공유 DB 로컬 환경에서는 활성화하지 않는다. 장애로 비활성화해도 pending 경로를 수동으로 지우지 않는다. 다시 활성화하면 이어서 복구한다.

## 격리 검증

Java: JDK 21에서 `./gradlew test --no-daemon`. JavaScript: `node --test scripts/swagger-auth.test.cjs`.

최종 실행 결과(2026-11-08 KST): Java 전체 **292 성공 / 0 실패 / 0 오류 / 0 스킵**, JavaScript **10 성공 / 0 실패 / 0 스킵**. `git diff --check`도 통과했다.

통합 테스트는 H2 PostgreSQL 모드의 격리 메모리 DB와 mock Storage/AI를 사용한다. V4/V5 SQL을 테스트 DB에서 실행하며 실제 Supabase에 접근하지 않는다. Storage 어댑터는 loopback HTTP 서버에서 400/404 NoSuchKey, 버킷/권한 오류, 부분 삭제 재시도 계약을 검증한다. H2 통과가 실제 PostgreSQL 배포 검증을 대신하지는 않는다.

검증 범위: 7일 경계·생성 시각 fallback, 10개 초과·과목 합산·사용자 격리, 처리 중 보호, PDF/PPTX·PNG 전체 삭제, 부분 실패·프로세스 재시작·DB 최종 저장 실패 후 재시도, 학습 데이터 보존, EXPIRED retry409, 처리 시작 10분 경계, 오래된 콜백 차단, 동시 retry/중복 정리, 스케줄러 기본 off, 커밋/롤백 이벤트, 실행 큐 거부, V5 기존 작업 유예. 기존 슬라이스 8/9 파이프라인 및 Swagger 인증 회귀 테스트도 함께 실행한다.

슬라이스 11은 `MaterialRetentionService`, 소유권 확인이 포함된 정리 트랜잭션, `MaterialStorage.delete()`의 멱등 계약을 재사용할 수 있다. 사용자 직접 삭제가 필요하다면 단원/답안 보존 정책을 별도로 결정한 뒤 연결한다.
