## 요청 및 응답

두 요청 모두 Bearer JWT가 필요하다. 한 엔드포인트를 scope로 구분한다.

### 세션 요약

`GET /api/subjects/8/report?scope=session&sessionId=12`

```json
{
  "today": {"minutes":24,"solved":3,"accuracy":0.5,"wrong":1},
  "feedback":"스택과 큐를 복습해 보세요."
}
```

위 예시는 정답 1개, 오답 1개, 채점 대기 1개인 세션이다. today는 JSON 계약상의 이름이며 현재 날짜 필터가 아니다. 과거 세션도 해당 세션의 전체 응답으로 계산한다.

- minutes: session.started_at부터 **요청 과목에 속한 마지막 응답**의 answered_at까지 경과한 분. 분 미만은 버리고, 시작/응답이 없거나 음수이면 0. ended_at 및 현재 시각은 사용하지 않는다.
- solved: 해당 세션·과목·사용자의 저장된 응답 수. 채점 대기를 포함한다.
- wrong: correct=false 응답 수. null은 오답으로 보지 않는다.
- accuracy: correct=true 수 / correct가 null이 아닌 수. 채점 완료 응답이 없으면 명시적 null이다. 자가 판정도 저장된 correct를 사용한다.
- feedback: 기존 session.feedback 원문. 미생성은 null이며 AI 호출·생성을 하지 않는다.

기존 AttemptService는 클라이언트 answeredAt을 저장하며 미래 시각만 서버 시각으로 제한한다. 오프라인 응답의 늦은 업로드 시각 대신 **저장된 실제 응답 시각**으로 계산한다. 보고서가 시각이나 답안을 재작성하지 않는다.

과목 소유권을 SubjectRepository.requireOwned로 검증하고, 세션 소유권과 session_question → question → category의 과목 연결도 확인한다. 존재하지 않거나 다른 사용자의 과목/세션, 요청 과목 문제가 없는 세션은 404다. 여러 과목이 섞인 REVIEW 세션은 요청 과목의 응답·마지막 시각만 집계한다. feedback은 세션 전체에 대한 저장 문구이며 과목별로 다시 생성하지 않는다.

### 과목 통계

`GET /api/subjects/8/report?scope=all`

```json
{
  "accuracyTrend":[{"date":"2026-11-08","accuracy":0.5,"answers":5}],
  "byCategory":[{"id":12,"accuracy":0.5},{"id":13,"accuracy":null}],
  "average":0.5
}
```

- accuracyTrend: KST 날짜 오름차순. answers는 채점 대기를 포함한 저장 응답 수이며 accuracy의 분모는 **채점 완료 응답 수**다. 예를 들어 정답 2·오답 2·대기 1이면 answers=5, accuracy=0.5다.
- report.min-answers(기존 기본값 5)보다 전체 응답 수가 작은 날짜는 그래프에서 제외한다. 설정값 3으로 변경하면 3개 이상인 날을 포함한다. 5개가 전부 채점 대기이면 날짜는 포함하지만 accuracy=null이다.
- byCategory: 해당 과목의 모든 단원. 정답률 오름차순 → 단원 ID 오름차순, null은 마지막이다. 미학습·채점 대기만 있는 단원은 null이다. 순서 자체가 취약 단원 순위이며 별도 랭킹 필드는 추가하지 않는다.
- average: 모든 날짜·단원의 정답 수 / 채점 완료 응답 수. 날짜별 비율의 단순 평균이 아니다. 그래프에서 제외된 소수 응답 날짜도 포함한다. 채점 완료가 없으면 null이다.
- 일반 학습과 오답노트 재응시, PREGEN/EXTRA를 모두 포함한다. 같은 문제도 다른 세션에서 다시 풀면 각각의 실제 응답으로 집계한다.

단원 자체가 없는 과목은 `{"accuracyTrend":[],"byCategory":[],"average":null}`이다. 응답 없는 날짜는 생성하거나 0으로 채우지 않는다. 프론트는 date를 날짜 축, accuracy를 0~1 값(표시 시 ×100%), answers를 응답 수로 사용한다. null 정답률은 0%가 아닌 미채점/미학습으로 표시한다.

## SQL 및 시간대

ReportRepository의 공통 응답 조회는 사용자·과목 조건을 적용하고 session.user_id도 검사한다. session_question은 EXISTS로 검사하므로 같은 세션의 다른 문제 수만큼 attempt가 중복되지 않는다. V2의 (session_id, question_id) UNIQUE와 기존 중복 전송 무시 정책도 유지한다.

일별 SQL의 핵심:

```sql
-- 소유권과 과목·세션 문제 연결을 검증한 answers CTE 이후
SELECT answered_at AT TIME ZONE 'Asia/Seoul' AS kst_time, correct
FROM answers;
-- kst_time의 YEAR/MONTH/DAY로 GROUP BY
-- COUNT(*) = answers, COUNT(correct) = 채점 완료 수
-- SUM(CASE WHEN correct=true THEN 1 ELSE 0 END) = 정답 수
-- HAVING COUNT(*) >= report.min-answers
```

KST 변환 후 EXTRACT(YEAR/MONTH/DAY)로 집계하고 LocalDate로 반환한다. PostgreSQL의 AT TIME ZONE 결과와 H2의 timestamp with time zone → DATE 캐스팅 차이를 피하며 서버/DB 기본 시간대에 의존하지 않는다. H2 세션을 UTC로 설정한 상태에서 14:59:59Z와 15:00:00Z가 다른 KST 날짜인지 검증한다.

단원 집계는 LEFT JOIN으로 미학습 단원을 보존하고 COUNT(correct), 조건부 SUM을 사용한다. 서비스가 단원별 원시 정답/채점 수를 합쳐 전체 평균을 계산하므로 정답률의 평균을 다시 평균내지 않는다. 세션은 소유권 포함 3회, 과목 전체는 소유권 포함 3회 SELECT로 처리한다. 단원별 N+1 쿼리는 없다.

CurrentUser.authenticatedId로 UUID만 추출하며 사용자를 자동 생성하지 않는다. 서비스는 @Transactional(readOnly=true)이고 API 구현에는 INSERT/UPDATE/DELETE, AI 호출, 상태 전이, 세션 종료가 없다.

## 파라미터와 Swagger 검증

- scope 누락/지원하지 않는 값, session scope의 sessionId 누락, 숫자 형식 오류·오버플로·0·음수 sessionId는 400 VALIDATION_ERROR.
- all scope의 양수 sessionId는 사용하지 않는다. 제공한 값 자체가 잘못되면 400이다.
- 인증 없음은 401, 없는/남의 리소스 및 과목 연결이 없는 세션은 404 NOT_FOUND.

Swagger 수동 순서:

1. Google 로그인 또는 Authorize로 본인 JWT를 설정한다.
2. 기존 과목 목록과 세션 응답에서 실제 소유한 ID를 확인한다. 문서의 8/12는 예시다.
3. GET /api/subjects/{id}/report에 scope=session, sessionId를 넣고 Execute한다. minutes·solved·wrong·accuracy와 feedback null/문구를 확인한다.
4. scope=all로 실행해 날짜 오름차순, 최소 응답 수 필터, 단원 정렬, 전체 평균을 확인한다.
5. Swagger의 **Example Value는 고정 예시**, **Server Response는 실제 DB 조회 결과**임을 구분한다.
6. 없는/남의 과목·세션 및 다른 과목 세션은 404인지, 파라미터 누락은 400인지 확인한다. 로그아웃 후에는 401이다.

공유 운영 DB에 시드를 실행하거나 답안을 테스트 목적으로 생성하지 않는다. 자동 검증은 별도 H2 메모리 DB로 실행한다.

테스트는 세션 시간의 누락/음수/분 미만/ended_at 불사용, 자가 판정, 채점 대기, 중복 응답 제약, 다과목 REVIEW, 일별 4/5/6개 경계, 설정 변경, KST 자정, 재응시, 사용자 격리, 정렬·가중 평균, 빈 데이터, JWT·파라미터·Swagger 및 조회 전후 데이터 불변성을 포함한다. FeedbackAiClient mock의 호출 없음도 검증한다.

실행 명령: JDK 21 `./gradlew test --no-daemon`, `node --test scripts/swagger-auth.test.cjs`.

최종 결과(2026-11-08 KST): **Java 전체 434 성공 / 0 실패 / 0 오류 / 0 스킵**, **JavaScript 10 성공 / 0 실패 / 0 스킵**. 신규 리포트 통합 테스트 26개를 포함한다. `git diff --check`도 통과했다. 현재 브랜치 `Feat/#32`, 수정 1개·신규 6개이며 staged 변경은 없다. 미병합 PR #57의 신규 SSE 테스트는 이 develop 기반 브랜치의 테스트 집합에 포함되지 않는다.

실제 PostgreSQL 실행 계획과 운영 부하는 검증하지 않았다. V1~V5 수정이나 신규 마이그레이션은 없으며 기존 세션/답안/채점/AI/피드백 로직과 .env를 변경하지 않았다. 운영 DB·Railway 쓰기, 유료 AI 호출, Commit/Push/PR/Merge는 수행하지 않았다. 슬라이스 18/19도 포함하지 않았다.

팀 정책 확인 사항:

- Issue의 “그날 응답” 중 채점 대기는 그래프 최소 응답 수에는 포함하지만 정답률 분모에는 제외한다. 이는 슬라이스 11과 일치하는 구현 기준이다.
- 다과목 세션의 minutes는 요청 과목 마지막 답안 기준의 경과 시간이며 실제 과목별 집중 시간의 합계가 아니다. feedback은 세션 전체 문구다.
- 재응시는 매 응답을 반영하므로 반복 학습이 전체 정답률에 가중된다. 피드백이 나중에 생성되면 재조회 시 문구가 나타난다.
- answered_at/feedback 또는 attempt의 유일성 계약을 변경하면 집계 담당에게 공유해야 한다.
