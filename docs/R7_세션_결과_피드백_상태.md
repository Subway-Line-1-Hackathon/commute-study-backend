# R7 — 세션 전체 결과와 피드백 상태

기준: 프론트엔드 API 요청서 2차(2026-11-13), [이슈 #80](https://github.com/Subway-Line-1-Hackathon/commute-study-backend/issues/80).
작업 기준은 원격 develop `954da4fc7337d5e85ce13a15d76cc6bfebc73dbe`, 브랜치는 `Feat/#80`이다.
첨부 요청서는 요구사항 참고 자료로 사용했으며, 실행 범위와 안전 제약은 사용자의 요청을 따른다.
R1~R5는 이미 병합되어 있다. 확인 시점에 열린 PR은 없었으며 R6 구조화 요약·TTS 필드는 백엔드에 없었다. R1~R6 구현은 변경하지 않는다.

## 요청과 응답

`GET /api/sessions/{id}/report`, Bearer JWT 필수.

```json
{
  "sessionId": 42,
  "today": {
    "answered": 30,
    "correct": 24,
    "accuracy": 0.8,
    "minutes": 24,
    "solved": 30,
    "wrong": 6
  },
  "feedback": null,
  "feedbackStatus": "PENDING"
}
```

- 세션 자체의 `user_id`로 소유권을 검증한다. 남의 세션과 없는 세션은 동일하게 404 `NOT_FOUND`, 인증 없으면 401이다. 숫자 형식 오류·범위 초과는 400, 존재하지 않는 0·음수 ID는 404다.
- READY/IN_PROGRESS/COMPLETED/ENDED 모두 조회할 수 있다. 답안·문제가 없는 본인 세션도 200이다.
- `today`는 오늘 날짜 필터가 아니라 해당 세션 전체 결과다. 여러 과목을 합산하며 다른 세션의 답안은 포함하지 않는다.
- `answered`와 `solved`는 저장된 본인 답안 수이며 채점 대기도 포함한다. `(session_id, question_id)` 유니크 제약과 `session_question` EXISTS 검사로 중복 집계를 방지한다. 세션에 포함되지 않은 문제 답안 및 다른 사용자의 답안은 제외한다.
- `correct`는 `correct=true` 개수, `wrong`은 `correct=false` 개수다. 자가 판정도 포함한다.
- `accuracy`는 기존 규칙대로 `correct / 채점 완료 답안 수`다. 채점 대기가 있으면 `correct / answered`와 다를 수 있다. 채점 완료가 없으면 0이 아닌 명시적 null이다.
- `minutes`는 시작부터 세션 전체 마지막 답안까지의 분을 내림한다. 시작·답안이 없거나 음수이면 0이다. 종료 시각·현재 시각은 사용하지 않는다.
- `feedback`은 null이어도 필드를 유지한다. 클라이언트는 `feedbackStatus=PENDING`일 때만 재조회한다.

기존 `GET /api/subjects/{id}/report?scope=session&sessionId=...` 및 `scope=all`은 유지한다. 기존 세션 응답은 `{today:{minutes,solved,accuracy,wrong},feedback}` 형태와 과목별 집계 의미를 그대로 사용한다. 새 API에서만 세션 ID·상태·`answered/correct`를 제공한다. 기존 공통 집계식·정답률·시간 계산과 `CurrentUser.authenticatedId()`를 재사용한다. 모든 리포트 GET은 조회만 수행하며 사용자 생성·AI 호출·상태 변경이 없다.

## 피드백 상태

`session.feedback_status`와 `feedback_status_reason`을 영속화한다. 상태를 `feedback=null`이나 경과 시간만으로 추정하지 않는다.

| 상태 | 의미 |
| --- | --- |
| PENDING | 새 세션의 기본 상태. 종료 전 또는 생성 대기·실행 중 |
| READY | 비어 있지 않은 AI 문구와 상태를 함께 저장한 경우 |
| SKIPPED | NEW_START/NEXT_DAY 종료, 채점된 답안 0개, 과거 종료 세션 소급 생성 생략 |
| FAILED | AI 예외·시간 초과·빈 응답, 작업 제출 거부 또는 처리 오류 |

종료 이벤트의 BEFORE_COMMIT에서 생략을 확정하므로 종료가 롤백되면 상태도 롤백된다. AFTER_COMMIT에서 전용 실행기에 제출하며 제출 거부는 별도 트랜잭션으로 실패를 저장한다. AI 호출 중에는 DB 트랜잭션을 유지하지 않는다. 조건부 UPDATE로 이미 확정된 결과를 뒤늦은 성공·실패가 덮지 않도록 한다.

최소 답안 정책은 기존과 동일하게 **채점 완료 1개 이상**이다. 리포트 그래프의 `report.min-answers=5`와는 별개다. 종료 이후 오프라인 답안이 추가되더라도 종료 이벤트가 다시 발행되지 않으므로 이미 생략되거나 완성된 피드백을 자동 재생성하지 않는다. 수치 결과는 조회 시점에 저장된 답안을 반영한다.

## 마이그레이션과 운영 경계

신규 [V8](../src/main/resources/db/migration/V8__add_session_feedback_status.sql)만 추가한다. 기존 V1~V7은 변경하지 않는다.

기존의 비어 있지 않은 피드백은 READY로 보존한다. 기존 종료 세션에 피드백이 없으면 당시 실패·생략·작업 유실을 구분할 수 없다. 따라서 과거 원인을 추정하지 않고 **소급 생성을 하지 않는 정책**으로 SKIPPED, 사유 `LEGACY_NOT_REGENERATED`를 기록한다. 실제 과거 실패 원인이 복원되었다는 뜻이 아니다. 종료 전 세션은 PENDING으로 시작한다.

V8 적용과 새 애플리케이션 전환은 리뷰 후 함께 진행해야 한다. 구버전 worker는 상태 컬럼을 갱신하지 못하므로 전환 중 구버전 피드백 작업을 중단·완료한 뒤 적용해야 한다. 이 작업에서는 운영 Supabase DB·Storage 접근, Railway 배포, 환경변수·키 변경 및 merge를 수행하지 않는다. 테스트 목적으로 서버를 운영 설정으로 기동하지 않는다.

프로세스 강제 종료나 DB 장애로 상태 저장 자체가 불가능한 경우 PENDING이 남을 수 있다. 현재 작업은 영속 작업 큐·재시작 후 자동 회수까지 도입하지 않는다. 경과 시간만으로 FAILED를 추정하는 것도 하지 않는다. 이 복구 보장은 후속 outbox/작업 lease 설계가 필요하다.

## 검증

Java 전체 테스트는 외부 인증·DB 연결을 차단한 기존 mock/H2 구성을 사용한다. 신규 회귀 범위는 여러 과목 합산, 레거시 응답 호환, 빈 세션·채점 대기·자가 판정, 소유권·인증·Swagger, GET 불변성, 피드백 성공·실패·생략·빈 응답, 커밋·롤백·작업 제출 거부 및 마이그레이션 backfill이다.

앞선 전체 실행에서는 638개 중 1개가 실패했으며, 그 항목은 `MaterialPipelineTest.errorsAreSanitizedAndNeverPublishProcessed`의 `UNSUPPORTED_FILE` 경우였다. 짧은 PROCESSING 상태를 기다리는 동안 이미 FAILED가 되어 assertion이 실패했고 해당 메서드 단독 재실행은 통과했다. 수정 전 develop `954da4f`의 별도 작업트리에서도 자료 처리·정리 두 suite를 함께 실행했을 때 36개 중 2개가 실패했고, 최초 실패 3개를 개별 실행하면 모두 통과했다. 다만 수정 전 develop 전체 실행은 609개 모두 통과했다. 따라서 정확히 같은 실패가 기존 develop에 재현됐다고 단정하지 않는다. 비동기 테스트의 간헐 실패 증거는 있지만 정확한 원인은 확정하지 않았으며 전체 테스트 통과로 보고하지 않는다. R7과 관계없는 자료 처리 구현·기존 테스트는 변경하지 않았다.

PostgreSQL 검증은 포트 공개와 외부 네트워크가 없는 새 로컬 컨테이너에서 `auth.users` 의존 테이블만 준비하여 실행했고 컨테이너를 제거했다. 실제 Flyway 기동·운영 JWT·Supabase·Railway 실연동 검증은 수행하지 않는다.
