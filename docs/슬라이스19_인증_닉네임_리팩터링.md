# 슬라이스 19 — 인증·닉네임 API 공통 구조

작업 브랜치: `Feat/#35` · 이슈: [#35](https://github.com/Subway-Line-1-Hackathon/commute-study-backend/issues/35)

## 구조와 호환성

기존 AuthController/NicknameController의 직접 SQL·JdbcTemplate 의존성을 제거했다.
두 컨트롤러는 요청·응답 매핑만 담당하고, UserService가 CurrentUser로 인증된 UUID를
추출하고 UserRepository를 호출한다. SQL은 UserRepository에서만 실행한다.
기존 UserService.getMe와 SettingsService의 정식 사용자·통학 설정 흐름은 유지한다.

| 경로 | 성공 응답 필드 | 사용자 생성 |
| --- | --- | --- |
| GET /api/auth/me | userId, email, nickname, nicknameSet | 없음 |
| GET /api/users/me/nickname | userId, nickname, nicknameSet | 없음 |
| PUT /api/users/me/nickname | userId, nickname, message | 없으면 생성 |
| GET /api/users/me | 기존 UserResponse 유지 | 기존 자동 생성 유지 |
| GET /api/users/me/settings | 기존 설정 응답 유지 | 기존 동작 유지, 설정 없으면 404 |
| PUT /api/users/me/settings | 기존 설정 저장 응답 유지 | 기존 동작 유지 |

레거시 조회에서 nickname/email이 없으면 JSON null을 포함한다. nicknameSet은 기존처럼
닉네임이 null이 아니고 blank가 아닐 때 true다. 저장 성공 메시지는 `닉네임 저장 성공`이다.
요청 본문의 userId는 인증 주체를 바꾸지 못한다.

닉네임 저장은 서비스 트랜잭션 안에서 기존 createIfAbsent(ON CONFLICT DO NOTHING)와
nickname UPDATE를 실행한다. 신규 사용자를 만들거나 기존 사용자 닉네임만 변경하며,
created_at·commute_profile·과목은 보존한다. 중간 실패 시 전체가 롤백된다.
동시 최초 저장도 하나의 사용자 행만 남으며 최종 닉네임은 마지막 쓰기가 결정한다.

## 닉네임과 오류 계약

NicknamePolicy를 레거시 저장과 SettingsRequest가 공유한다.
문자열을 기존 `String.trim()`으로 정규화한 뒤 Unicode code point 기준 2~10자를 허용한다.
UTF-16 char 개수나 화면상 글자(grapheme) 개수를 세지 않는다.
기존 공백 정책을 유지하므로 strip()이나 새로운 Unicode 공백 정책으로 확대하지 않는다.

NicknameRequest의 전용 Jackson 역직렬화기는 숫자·boolean·배열·객체를 문자열로
변환하지 않는다. 누락/null/빈 문자열/공백뿐인 문자열/1자/11자와 잘못된 JSON은 400이다.
숫자·boolean의 문자열 강제 변환을 허용하던 입력은 이번 작업에서 명시적으로 거부한다.
정식 설정의 oneWayMin 필수 및 10~120 범위, 기존 오류 처리는 그대로다.

닉네임 길이·누락 오류 예시:

```json
{"code":"VALIDATION_ERROR","message":"닉네임은 2~10자로 입력해주세요.","details":null}
```

JSON 타입·문법 오류 예시:

```json
{"code":"VALIDATION_ERROR","message":"입력 형식 또는 범위가 올바르지 않습니다.","details":null}
```

정식 설정의 Bean Validation 오류는 기존처럼 details에 필드별 오류를 포함할 수 있다.
서비스의 ApiException과 JSON 읽기 오류는 기존 GlobalExceptionHandler를 사용한다.

## Security 필터 인증 실패

JsonAuthenticationEntryPoint를 SecurityConfig의 exceptionHandling과
oauth2ResourceServer 양쪽에 등록했다. MVC 진입 전의 인증 누락, 잘못된 Bearer 형식,
유효하지 않은/만료된 JWT 및 서명 검증 오류를 아래 응답으로 통일한다.

```json
{"code":"UNAUTHORIZED","message":"인증에 실패했습니다.","details":null}
```

HTTP 401, Content-Type application/json;charset=UTF-8, WWW-Authenticate: Bearer를 반환한다.
ErrorResponse와 CommonErrorCode.UNAUTHORIZED를 사용하며, 예외 메시지·토큰·키 정보를
응답에 포함하지 않는다. 인증된 JWT의 잘못된 subject UUID는 CurrentUser의 기존 공통
예외 처리로 401을 반환한다.

JWT decoder 및 application.yaml의 ES256, issuer, audience=authenticated, 만료 검증
설정은 변경하지 않았다. Stateless/CSRF/CORS 및 Swagger·health 공개 경로도 유지한다.
401의 Content-Type과 body가 통일되므로 프론트는 빈 body나 OAuth 오류 문자열에 의존하면 안 된다.

## 프론트엔드 전환 합의

레거시 세 경로는 삭제하지 않고 Swagger deprecated와 대체 경로 안내를 유지한다.

- 로그인 상태는 GET /api/users/me로 전환하되 email/nicknameSet 대신 정식 응답을 매핑해야 한다.
  정식 조회는 사용자를 자동 생성한다는 차이도 반영한다.
- 닉네임·통학 화면은 GET/PUT /api/users/me/settings로 전환한다.
  정식 PUT에는 oneWayMin이 필수이므로 닉네임만 보내던 요청의 URL만 바꾸면 안 된다.
- 설정이 없는 GET settings의 404와 레거시 null 응답 차이를 처리한다.
- 공통 code/message/details 오류 처리, 401 시 재로그인/토큰 갱신 흐름,
  숫자 닉네임 거부 정책을 프론트와 확인한다.
- 호출부 이관 확인과 폐기 일정 합의 전까지 레거시를 유지한다.

## Swagger 확인 절차

자동 테스트는 인증 없이 /v3/api-docs를 조회하여 여섯 operation과 레거시 deprecated,
200/401 응답 및 PUT 400 예시가 존재함을 확인한다.

배포 전 아래 브라우저 검증은 별도로 수행한다. 이번 작업에서 실제 Supabase 로그인이나
운영 데이터 쓰기는 실행하지 않았다.

1. Swagger UI에서 여섯 경로와 레거시 deprecated 표시, 대체 안내, 오류 예시를 확인한다.
2. Authorize 없이 조회 및 PUT을 실행해 공통 401 JSON을 확인한다.
3. 테스트 계정의 정상 JWT로 레거시 두 조회의 기존 필드와 null 처리를 확인한다.
4. 격리된 개발 환경에서 nickname=동현으로 PUT 후 조회한다. 통학 설정 없이도 저장되어야 한다.
5. 누락/null/공백/1자/11자/숫자/boolean 닉네임과 잘못된 JSON이 400인지 확인한다.
6. 정식 settings 저장·조회, users/me 상태·과목·통학 설정이 유지되는지 확인한다.
7. 만료/변조 JWT로 같은 401 JSON을 확인하고 정상 로그인·갱신·CORS 흐름을 점검한다.

## 범위와 남은 확인

스키마·V1~V5·환경변수·.env·Supabase/Google OAuth 설정은 변경하지 않았다.
신규 마이그레이션이나 Railway 환경변수도 없다. 운영 DB/Storage/AI 호출 검증은 수행하지 않았다.
H2 테스트는 실제 PostgreSQL FK·RLS 및 배포된 Supabase 키 검증을 대체하지 않는다.
배포 전 테스트 계정으로 Google 로그인/토큰 갱신과 실제 프론트 호출부 전환을 확인해야 한다.
자료 정리 비동기 테스트의 일회성 실패는 CI에서 재발 여부를 확인할 필요가 있다.

별도 작업인 wrongNotes 세션 categoryIds 지정 시 RESOLVED 전환 누락은 수정하지 않았다.
자료 업로드/정리·AI 처리·세션·채점·SSE·학습 리포트·오답노트 코드는 변경하지 않았다.
Commit, Push, PR, Merge는 실행하지 않았다.
