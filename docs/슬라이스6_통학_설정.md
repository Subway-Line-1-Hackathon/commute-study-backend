# 슬라이스 6: 닉네임 및 통학 설정

## 요청과 응답

두 API 모두 기존 Supabase Bearer JWT 인증을 사용한다.

```http
PUT /api/users/me/settings
Authorization: Bearer <Supabase access token>
Content-Type: application/json

{
  "nickname": "동현",
  "oneWayMin": 50,
  "fromStation": "수원역",
  "toStation": "서울역"
}
```

성공 시 HTTP 200:

```json
{"nickname":"동현","studyMin":50,"mode":"CURRICULUM"}
```

`GET /api/users/me/settings`의 성공 응답:

```json
{
  "nickname": "동현",
  "oneWayMin": 50,
  "fromStation": "수원역",
  "toStation": "서울역",
  "studyMin": 50,
  "mode": "CURRICULUM"
}
```

설정이 없으면 기존 공통 에러 계약의 HTTP 404 `NOT_FOUND`를 반환한다.
이 경우 전체 조회 트랜잭션이 롤백되므로 신규 사용자 자동 생성도 커밋하지 않는다.
최초 설정 PUT 또는 기존 `/api/users/me`를 호출하면 사용자 행이 생성된다.

## 검증 및 계산

- 닉네임은 기존 API와 동일하게 `trim()` 후 Unicode code point 2~10자로 검사한다.
- 닉네임 중복을 허용한다. Google 이름은 사용하지 않는다.
- `oneWayMin`은 JSON 정수 10~120만 허용한다. `"50"`, `50.0`, `50.5`, boolean은 400이다.
- 필수값 누락·NULL, 잘못된 타입·JSON은 HTTP 400 `VALIDATION_ERROR`다.
- 역 이름은 선택 문자열이며, DB varchar(50)에 맞춰 최대 50자로 검증한다.
  생략하거나 NULL을 보내면 NULL로 저장된다. PUT 수정 시 생략한 역 이름은 기존 값이 지워진다.
- Bean Validation 및 기존 `ErrorResponse`/`GlobalExceptionHandler`를 사용한다.
  JSON 파싱 오류도 공통 400 형식으로 처리하도록 handler를 추가했다.
- `studyMin = oneWayMin`. 기존 `StudyMode.of(minutes, studyProperties.getCurriculumMinMinutes())`를 사용한다.
  기본 20분 미만은 REVIEW, 20분 이상은 CURRICULUM이다.

## 저장과 동시성

`SettingsService.save`의 하나의 쓰기 트랜잭션 안에서:

1. `CurrentUser.ensureUser(jwt)`로 사용자 존재를 보장한다.
2. 인증된 UUID의 `app_user.nickname`을 UPDATE한다. 이 행 잠금으로 동일 사용자 저장을 직렬화한다.
3. 해당 사용자의 `commute_profile`을 UPDATE하고, 행이 없으면 INSERT한다.

UPDATE-then-INSERT 방식의 upsert이며, 2단계의 사용자 행 잠금을 선행하므로 동시 최초 저장도 안전하다.
어느 저장 단계든 실패하면 사용자 자동 생성·닉네임·통학 설정을 모두 롤백한다.
Repository 저장 메서드는 반드시 위 서비스 트랜잭션 안에서 호출한다.
다른 사용자의 UUID를 요청에서 받지 않으며 조회와 쓰기 모두 인증된 사용자 UUID로 제한한다.
`departure_time`, `notify_enabled`는 읽거나 갱신하지 않는다.

V2의 `from_station`, `to_station` NOT NULL 해제를 확인했다.
기존 Flyway 파일 수정이나 새 마이그레이션은 없다.

## 호환성과 다음 슬라이스

`/api/auth/me`, `/api/users/me`, `/api/users/me/nickname` GET·PUT은 유지한다.
닉네임 GET·PUT에 OpenAPI deprecated 표시만 추가했다.
설정 저장 후 과목이 없으면 `/api/users/me` 상태는 AUTHENTICATED이며, 과목까지 있으면 ACTIVE다.
기존 Swagger Google 로그인과 자동 Bearer 인증 경로를 그대로 사용한다.

슬라이스 7 서비스에서는 `CurrentUser`를 주입한 뒤 쓰기 트랜잭션 안에서
`UUID userId = currentUser.ensureUser(jwt);`를 호출하고, 이 UUID로 과목을 저장하면 된다.

## 검증과 Swagger 확인

Java 21 전체 테스트 106개, Swagger 인증 JavaScript 테스트 10개가 모두 통과했다.

Java 테스트는 운영 DB에 연결하지 않는 기존 H2 PostgreSQL-mode fixture를 사용한다.
경계값·Unicode·타입 오류·반복 저장·사용자 격리·서명된 만료 토큰·6개 동시 저장을 검증한다.
테스트 DB에만 실패 조건을 걸어 신규 사용자 및 기존 사용자 저장의 트랜잭션 롤백도 확인한다.
설정 기준값 변경 시 PUT·GET 모드가 동일하게 바뀌는지 검증한다.
기존 닉네임 PUT은 기존 JdbcTemplate mock 회귀 테스트로 검증한다.

```powershell
$env:JAVA_HOME='C:\Program Files\Java\jdk-21.0.12.1'
.\gradlew.bat test --no-daemon
node --test scripts/swagger-auth.test.cjs
```

Swagger 수동 확인:

1. 서버 실행 후 `/swagger-ui/index.html`에서 Google 로그인한다.
2. 설정 PUT의 예시를 실행한 뒤 GET으로 저장된 값과 모드를 확인한다. 토큰을 별도로 복사할 필요는 없다.
3. 시간을 19분으로 수정해 REVIEW, 20분으로 수정해 CURRICULUM인지 확인한다.
4. 9분 또는 닉네임 1자를 보내 400 `VALIDATION_ERROR`인지 확인한다.
5. `/api/users/me`의 설정 반영과 과목 유무에 따른 상태를 확인한다.

실제 Google 계정 로그인과 PostgreSQL의 잠금 동작은 이 테스트가 대체하지 않는다.
운영 DB 쓰기 테스트는 실행하지 않았으며, 별도 테스트 계정/격리된 PostgreSQL에서 최종 확인해야 한다.
