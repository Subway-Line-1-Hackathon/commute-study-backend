# 슬라이스 11 — 단원 진도·정답률 및 해설 조회

기준: [GitHub Issue #26](https://github.com/Subway-Line-1-Hackathon/commute-study-backend/issues/26), 최신 develop `544f126`, 작업 브랜치 `Feat/#26`.

## API와 소유권

- `GET /api/subjects/{id}/categories`: 현재 사용자의 단원 통계와 추천 ID. `SubjectRepository.requireOwned()`로 과목 소유권을 확인하고 집계 SQL에서도 사용자/과목 조건을 적용한다. 다른 사용자 과목과 없는 과목은 모두 404 `NOT_FOUND`. 각 단원에 `materialId`(단원이 나온 자료)와 `summary`(단원 요약, 없으면 null)를 포함한다(#72).
- `GET /api/questions/{id}/explanation`: question → category → subject의 사용자 ID를 확인한 뒤 `explanation`, `sourcePage` 두 필드만 반환한다. 없는 문제와 남의 문제는 모두 404. 정답은 반환하지 않는다.
- 두 API 모두 기존 Spring Security Bearer JWT 인증을 사용한다. `CurrentUser.authenticatedId()`는 검증된 JWT의 UUID만 확인하며 DB 행을 생성하지 않는다. 기존 `ensureUser()`의 자동 생성 동작은 유지한다. 새 서비스는 `@Transactional(readOnly=true)`이며 SELECT만 실행한다.
- 자료 상태로 조회를 제한하지 않으므로 EXPIRED 자료의 단원·해설도 계속 조회할 수 있다. 해설/근거 쪽수가 없는 기존 행은 명시적 null을 반환한다.

## 집계 SQL

단원 개수와 무관하게 과목 소유권 확인 1회 + 통계 집계 1회다. 해설은 소유권 조인을 포함한 SQL 1회다. 세션·채점 서비스에 의존하지 않는다.

`StudyReadRepository`는 대상 단원을 `owned_categories` CTE로 제한한 뒤 문제 수와 응답 집계를 각각 수행하고 LEFT JOIN한다. 반복 응답으로 문제 분모가 늘어나는 조인 곱셈을 방지한다. 표준 CASE, COUNT, SUM, MAX, COALESCE를 사용하며 H2 PostgreSQL 모드에서 검증한다.

| 항목 | 계산 |
| --- | --- |
| PREGEN 분모 | 해당 단원의 `origin='PREGEN'` 문제 수. 고정 40을 사용하지 않음 |
| 풀이 완료 분자 | 현재 사용자 응답 중 `correct IS NOT NULL`인 PREGEN 문제의 `COUNT(DISTINCT question_id)` |
| progress | 분자 / 분모, 0~1. PREGEN 0개이면 0 |
| accuracy | 현재 사용자 `correct=true` 응답 수 / `COUNT(correct)`. 채점 완료 응답 0개이면 null |
| lastStudiedAt | 현재 사용자 `MAX(attempt.answered_at)`, 채점 대기와 EXTRA도 포함. 응답이 없으면 null |

정답률에는 반복 풀이 각각, EXTRA, `self_judged=true`인 자가 판정을 모두 포함한다. 자가 판정도 저장된 `correct`를 기준으로 계산한다. pending(`correct IS NULL`)은 정답률 및 풀이 완료 진도에서 제외한다. 오답도 풀이를 완료했으므로 진도에는 포함한다. EXTRA는 진도의 분자·분모 모두 제외한다.

반환 시각은 ISO 8601 offset 형식이다. DB/JDBC에 따라 UTC로 표현될 수 있으며 예시의 KST와 같은 시점을 뜻한다. 추천의 시간 비교는 offset 문자열이 아니라 Instant 기준이다.

## 상태와 추천

`questionStatus`는 DB의 PREPARING/AVAILABLE을 그대로 반환한다. `state`는 다음 우선순위다.

1. questionStatus PREPARING → PREPARING(진도와 무관하게 우선)
2. progress 0 → NOT_STARTED
3. 0 < progress < 1 → IN_PROGRESS
4. progress 1 → COMPLETED

`CategoryRecommendation`에 임시 정책을 분리했다. AVAILABLE 중 IN_PROGRESS의 최근 학습 시각이 가장 늦은 단원을 우선한다. 없으면 NOT_STARTED 중 `category.order, id` 순으로 첫 단원을 추천한다. 동일 학습 시각이면 동일 단원 순서를 유지한다. 대상이 없으면 recommendedId=null이다. PREPARING과 COMPLETED는 추천하지 않는다.

문제가 0개인 AVAILABLE 단원은 요구된 상태 규칙대로 NOT_STARTED이며 추천 후보에 포함한다. 기획에서 실제 문제 보유를 추천 조건으로 추가할지는 후속 합의 사항이다.

## Swagger 확인 순서

1. 운영 DB와 분리된 개발 DB 또는 승인된 기존 환경에서 Swagger UI를 연다. 로컬 공유 DB에 시드를 실행하지 않는다.
2. Google 로그인 또는 Authorize에 유효한 사용자 JWT를 입력한다.
3. 기존 `GET /api/subjects`에서 본인의 과목 ID를 확인한다.
4. `GET /api/subjects/{id}/categories`를 실행해 order/id 순서, 진도, 정답률, 마지막 시각과 추천을 확인한다. 기존 풀이 기록으로 검증하며 이번 조회 기능은 데이터를 생성하지 않는다.
5. 본인 문제 ID로 `GET /api/questions/{id}/explanation`을 실행한다. 해설과 쪽수만 보이는지 확인한다. 이미 EXPIRED인 자료도 조회 가능하다. 확인을 위해 원본을 강제 삭제하거나 만료시키지 않는다.
6. 다른 사용자/없는 과목·문제 ID는 404, 로그아웃 후 호출은 401인지 확인한다. Swagger의 각 API에 Bearer, 200 예시, 404 설명이 표시된다.

## 검증 및 기존 기능과의 경계

자동 테스트는 격리 H2 DB + mock JWT decoder를 사용하며 실제 Supabase/Storage를 호출하지 않는다. 테스트 fixture의 session/attempt는 V1/V2의 참조 관계와 `(session_id, question_id)` 유일성을 반영한다. 실제 PostgreSQL 실행 계획·부하 검증은 수행하지 않았다.

- 상태 네 가지, 빈 과목, PREGEN 0개, 반복 응답, EXTRA 제외, 채점 대기, 자가 판정, 사용자 격리, 마지막 학습 시각, 추천 순서 및 동률을 검증한다.
- JWT 필수, 잘못된 사용자 UUID, 없는/남의 과목·문제, null 해설, EXPIRED 조회, 조회 전후 모든 관련 행 불변성, 신규 사용자 미생성을 검증한다.
- `/v3/api-docs`에서 두 경로의 Bearer와 200/404 응답 문서 존재를 검증한다.
- 실행 명령: JDK 21 `./gradlew test --no-daemon`, `node --test scripts/swagger-auth.test.cjs`.

최종 결과(2026-11-08 KST): **Java 전체 313 성공 / 0 실패 / 0 오류 / 0 스킵**, **JavaScript 10 성공 / 0 실패 / 0 스킵**. 신규 테스트는 API/격리 DB 17개와 추천 정책 단위 테스트 4개다. `git diff --check`도 통과했다.

첫 전체 실행에서는 기존 `MaterialRetentionTriggersTest.enabledHooksRunOnlyAfterCommitAndNotAfterRollback`가 2초 내 mock 호출을 확인하지 못해 1건 실패했다. 해당 테스트와 운영 코드를 수정하지 않고 최종 전체 실행에서 통과했다. 간헐적 실행 타이밍 문제 가능성이 있어 CI에서 재발 여부를 관찰한다.

작업 종료 브랜치 `Feat/#26`, 수정 2개·신규 8개, staged 변경 없음.

V1~V5, Storage/만료 서비스, 문제 생성·답안·채점·세션·오답노트 구현은 변경하지 않았다. 새 마이그레이션·운영 환경변수는 없다. 기존 API 경로와 충돌하지 않는 GET 경로 두 개만 추가했다. `.env`를 수정하거나 운영 DB에 쓰지 않았다. Commit/Push/PR/Merge도 실행하지 않았다.

팀 후속 확인: Issue #26의 임시 추천/완료 정책, 채점 대기를 진도에서 제외하는 풀이 완료 정의, AVAILABLE이지만 문제 0개인 단원의 추천 처리. attempt.correct/self_judged/answered_at 또는 question.origin 스키마 변경 시 집계 담당자에게 공유해야 한다. 이 항목들은 현재 명시된 구현 기준으로 동작하며 구현 차단 사항은 아니다.
