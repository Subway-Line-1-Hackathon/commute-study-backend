# PR #81 — 자료 비동기 테스트 실패 분석과 수정

검증일: 2026-11-13 KST. 비교 기준은 수정 전 `develop@954da4f`와 R7 `Feat/#80@b5b308d`다. 두 대상 테스트와 관련 파이프라인·정리 서비스 코드는 두 커밋에서 동일했다. 비교용 별도 작업트리에는 운영 설정을 사용하지 않았고, 테스트는 mock 및 로컬 H2로 실행했다.

전체 2회차의 PNG 재시도 테스트는 최초 PR 검증과 같은 `available()` 검사에서 실패했다. 기대한 AVAILABLE 단원은 1개지만 실제로 0개였다. 다른 자료 테스트에서는 PROCESSING을 기다릴 때 이미 FAILED가 되는 실패도 발생했다. 단독 실행 성공만으로 정상이라고 판단할 수 없는 실행 순서 경합이었다.

정리 테스트 자체의 실패는 이번 develop 반복 실행에서는 재현되지 않았다. 대신 동일한 develop/feature 클래스 각각에 대해 Mockito 검증 스레드와 worker의 순서를 고정한 별도 probe로 아래 잠금 경합을 재현했다. 자연 발생 실패와 제어된 재현을 구분한다.

## 원인 1: 완료된 future의 후속 작업이 AFTER_COMMIT 호출 스레드에서 실행

`supplyAsync(...).thenCompose(...)`의 첫 작업이 후속 작업을 등록하기 전에 끝나면, `thenCompose`는 등록하는 스레드에서 즉시 실행될 수 있다. 첫 작업을 executor에 보냈다는 사실만으로 다음 작업도 같은 executor에서 실행된다고 보장되지 않는다.

자료·문제 생성은 AFTER_COMMIT 이벤트에서 시작한다. 이 콜백 중에는 Spring이 이미 커밋한 원래 트랜잭션의 플래그와 JDBC 연결을 아직 호출 스레드에 바인딩하고 있다.

- `MaterialProcessor`: 이 스레드에서 AI를 호출하면 테스트의 트랜잭션 분리 검증에 실패하여 자료가 FAILED가 된다.
- `QuestionPregenService`: 문제 저장·AVAILABLE 갱신이 원래 연결을 재사용하면 이후 커밋이 없어 다른 연결에서 결과가 보이지 않는다. 생성 완료 로그만으로 저장 완료를 판단할 수 없었던 이유다.

두 후속 작업을 각각 기존 전용 executor의 `thenComposeAsync`로 실행하도록 바꿨다. API, 문항 수·유형, 재시도·오류 정책은 변경하지 않았다. R7에서 새로 변경한 코드 때문에 생긴 기능 회귀가 아니라, 기존 코드의 실행 경계 결함이었다.

## 원인 2: timeout 검증이 synchronized mock의 잠금을 점유

`MaterialRetentionService.cleanUser`는 `synchronized` 메서드다. Mockito inline mock에 `verify(service, timeout(2000)).cleanUser(...)`를 호출하면 검증 스레드가 그 메서드의 모니터를 잡은 채 호출을 기다릴 수 있다. 이때 worker는 같은 모니터 진입을 기다리므로 검증이 기다리는 호출 자체를 수행하지 못한다.

develop/feature 두 클래스의 제어된 재현에서 `ThreadMXBean`으로 다음 상태를 확인했다.

```text
worker=retention-cleanup-worker state=BLOCKED
lockOwner=verification-monitor-owner
verify(timeout) -> WantedButNotInvoked
검증 스레드의 모니터 해제 후 동일 worker 호출 완료
```

실제 단일 worker executor에 barrier Future를 넣어 **기존과 같은 2초 한도**로 선행 작업 완료를 기다린 뒤 일반 `verify`를 수행하도록 테스트를 수정했다. 커밋 전 미실행, 롤백·트랜잭션 밖 이벤트 미실행을 유지하고, 큐가 비워진 뒤 부정 검증과 `verifyNoMoreInteractions`까지 확인한다. 정리 서비스의 프로덕션 코드는 변경하지 않았다.

## 결정적인 회귀 검증

테스트 전용 `CompletingWorkerExecutor`는 첫 작업을 실제 worker에서 끝낸 뒤 `execute`가 반환되게 해, future가 후속 작업 등록 전에 완료되는 순서를 고정한다. 실제 H2 트랜잭션의 afterCommit에서 호출하고 원래 스레드에 트랜잭션 플래그·연결이 남아 있는 것도 확인한다.

| 테스트 | 수정 전 R7 코드 + 새 테스트 | 수정 후 |
| --- | --- | --- |
| `MaterialProcessorTest.alreadyCompletedClaimStillCallsAiOutsideAfterCommitResources` | 기대 worker 대신 Test worker에서 AI 호출되어 실패 | 통과 |
| `QuestionPregenServiceTest.alreadyCompletedPagesStillCommitsGeneratedResultOutsideAfterCommitResources` | 독립 연결에서 AVAILABLE 대신 PREPARING을 읽어 실패 | 통과 |

새 테스트만 원본 R7 작업트리에 복사하여 **수정 전 2개 모두 실패, 수정 후 2개 모두 성공**을 확인했다. 임의 sleep이나 시간 제한 증가 없이 같은 실행 순서에서 수정 효과를 검증했다. 원래 `MaterialPipelineTest`의 검증 코드는 변경하지 않았다.
