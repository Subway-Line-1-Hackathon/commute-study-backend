## 지원 범위와 API

PDF/PPTX **파일 1개** 또는 PNG **1~20장**, `kind=LECTURE`를 지원한다.
PNG는 같은 multipart `file` 필드를 반복해서 전송하며, 전송 순서가 쪽 순서다.
파일명으로 정렬하지 않는다. PDF/PPTX와 PNG 혼합 또는 PDF/PPTX 여러 개는 거절한다.
PAST_EXAM은 P1 및 AI 처리 계약 합의 전이므로 거절한다.

### 업로드

`POST /api/subjects/{id}/materials`, Bearer JWT, multipart/form-data:

- `file`: PDF/PPTX 1개 또는 전송 순서대로 이미지(PNG·JPG, 섞어도 됨) 1~20장 (JPG는 #66에서 추가)
- `kind`: `LECTURE`

성공 HTTP 201:

```json
{"materialId":1,"status":"UPLOADED"}
```

Storage 업로드와 material 커밋이 끝나면 AI 완료를 기다리지 않고 반환한다.
백그라운드 처리가 이미 시작됐더라도 이 응답은 업로드 접수 결과를 나타낸다.

확장자와 Content-Type을 함께 검사한다. PDF는 `application/pdf`, PPTX는
`application/vnd.openxmlformats-officedocument.presentationml.presentation`만 허용한다.
PNG의 Content-Type은 `image/png`다.
PPTX는 기존 DB/AI 계약에 맞춰 file_type=PPT로 저장한다. 구형 PPT는 거절한다.
파일 내용의 바이러스 검사나 포맷 전체 파싱을 수행하는 것은 아니다.

- 30 × 1024 × 1024 bytes 초과: HTTP 413 `FILE_TOO_LARGE`
- 미지원 파일·MIME 불일치: HTTP 400 `UNSUPPORTED_FILE_TYPE`
- 빈 파일·PNG 21장 이상·혼합 형식·PDF/PPTX 복수·kind 오류: HTTP 400 `VALIDATION_ERROR`
- 소유하지 않은 과목과 없는 과목: HTTP 404 `NOT_FOUND`
- Storage 오류/미설정: HTTP 502 `STORAGE_UNAVAILABLE`

PDF/PPTX 쪽수는 업로드 단계에서 세지 않는다. AI의 PAGE_LIMIT_EXCEEDED는 FAILED로 처리한다.
AI 성공 응답도 pageCount 1~100, 페이지 번호·중복·누락 및 category 범위를 방어 검사한다.

### 상태

`GET /api/materials/{id}/status`, HTTP 200:

```json
{"status":"PROCESSING","categoryCount":0}
```

```json
{"status":"READY","categoryCount":1}
```

```json
{"status":"FAILED","categoryCount":0,"error":"텍스트를 추출할 수 없습니다."}
```

진행률은 없다. READY는 단원화 완료이며, 문제 생성 완료는 슬라이스 9의 AVAILABLE 상태다.
타인 자료와 없는 자료는 동일하게 404다.

### 재시도

`POST /api/materials/{id}/retry`, 성공 HTTP 202:

```json
{"materialId":1,"status":"PROCESSING"}
```

FAILED이며 보관 기한이 남은 자료만 원자적 UPDATE로 PROCESSING을 선점한다.
동시 요청 중 하나만 성공하고 나머지는 409 `STATE_CONFLICT`다.
READY/PROCESSING/UPLOADED/EXPIRED 또는 보관 기한이 지난 자료도 409다.
기존 객체를 재사용하고 새 서명 URL로 AI-01을 호출한다.

## Storage와 운영 환경

DB의 file_url에는 `bucket/user-UUID/random-UUID.pdf`(또는 pptx/png) 형태의 객체 참조만 저장한다.
원본 파일명은 file_name에 따로 저장하며 경로 부분을 제거한다.
PNG 묶음은 material 한 건과 `material_file(material_id, page_order, file_url)` 행 1~20개로 저장한다.
page_order는 1부터 시작하며 PK와 1~20 CHECK 제약이 있다. material 삭제 시 하위 행은 CASCADE 삭제된다.
material.file_url은 첫 이미지 참조, file_name은 첫 이미지 파일명, size는 전체 이미지 바이트 합계다.
V4는 기존 PNG material이 있다면 첫 파일을 page_order=1로 보존한다.
PDF/PPTX의 기존 단일 참조 방식은 유지한다.
업로드 전 버킷이 private인지 확인한다. public 버킷은 거절한다.
HTTP 리다이렉트를 따라가지 않고, 서명 URL은 동일 scheme/host/port 및 예상 객체 경로인지 검사한다.
서버 디스크에 자료를 영구 저장하지 않으며 multipart threshold를 35MB로 설정해
허용되는 파일을 메모리에서 처리한다. multipart 요청 상한은 605MiB(20×30MiB+multipart 여유)로 조정했다.
최대 PNG 묶음은 파일 데이터만 600MiB이므로 **메모리와 동시 업로드 수를 운영에서 관리해야 한다**.
이 작업에서 임의의 더 작은 파일/묶음 상한이나 디스크 임시 저장을 추가하지 않았다.

전체 파일의 개수·확장자·MIME·크기를 먼저 검증한 후 Storage 업로드를 시작한다.
Storage 중간 실패 시 material 행을 생성하지 않고, 해당 묶음에서 업로드를 시도한 모든 객체를 보상 삭제한다.
material 또는 material_file 저장 실패 시 DB 전체를 롤백하고 업로드한 모든 객체를 보상 삭제한다.
한 객체 삭제가 실패해도 나머지 삭제는 계속 시도한다.
삭제까지 실패하면 원문·비밀 키 없이 userId와 객체 참조만 운영 로그에 남긴다.
Storage 인증 정보·서명 URL은 응답이나 DB 오류 메시지에 저장하지 않는다.

환경변수(이름만 문서화했으며 실제 값과 운영 설정은 변경하지 않음):

| 변수 | 의미 |
|---|---|
| SUPABASE_URL | 기존 프로젝트 URL, HTTPS, 끝 슬래시/경로 없음 |
| SUPABASE_STORAGE_BUCKET | 미리 준비한 비공개 버킷 |
| SUPABASE_STORAGE_KEY | 서버 전용 service_role JWT 또는 sb_secret 키 |
| SUPABASE_HOST | AI 서버와 일치하는 Supabase 호스트명, scheme/경로 제외 |
| AI_SERVER_URL | 기존 AI 서버 주소 |
| AI_INTERNAL_KEY | 기존 AI 서버와 공유하는 내부 키 |
| AI_SIGNED_URL_TTL_MINUTES | 기본 10분, ai.signed-url-ttl-minutes에 연결 |

SUPABASE_PUBLISHABLE_KEY/anon 키를 관리자 키 대체물로 사용하지 않는다.
서버 전용 키는 프론트·Swagger 인증 설정에 전달하지 않는다.
SUPABASE_HOST가 비어 있으면 백엔드는 SUPABASE_URL 호스트를 검증 기준으로 사용하지만,
AI 서버에는 그 호스트를 별도로 정확히 설정해야 한다.
버킷 생성이나 공개 범위 변경은 이 구현이 수행하지 않는다.
Storage API는 [Supabase 공식 REST 문서](https://supabase.com/docs/reference/self-hosting-storage)를 참고했다.

## 비동기·트랜잭션·이벤트

1. 기존 CurrentUser와 SubjectRepository.requireOwned로 사용자와 과목 소유권 확인
2. DB 트랜잭션 밖에서 Storage 업로드
3. 짧은 트랜잭션으로 UPLOADED material 및 PNG material_file 저장, expires_at=현재+material.retention-days(기본 7일)
4. 트랜잭션 내부에서 MaterialQueuedEvent 및 MaterialUploadedEvent 발행
5. 커밋 후 기존 aiExecutor에 처리 예약, PROCESSING 원자적 선점
6. DB 트랜잭션 밖에서 새 서명 URL과 기존 MaterialAiClient.process 호출(PNG는 page_order 순서대로 전체 URL 전달)
7. 응답 검증 후 별도 트랜잭션에서 material_page·category 저장 및 READY 전환
8. 같은 트랜잭션 안에서 기존 MaterialProcessedEvent 발행
9. 커밋 후 기존 QuestionPregenEventListener가 읽어 AI-02·문제 저장·AVAILABLE 처리

단원은 항상 PREPARING으로 저장하고, Markdown summary는 변형하지 않는다(최대 1500 code points).
pageStart ≥ 1, pageStart ≤ pageEnd ≤ pageCount를 검증한다.
저장 중 실패하면 READY 전환·쪽 텍스트·단원을 모두 롤백하고, 별도 트랜잭션으로 FAILED를 기록한다.
실패/롤백 시 MaterialProcessedEvent가 전달되지 않는다.
슬라이스 8에서는 슬라이스 9 서비스를 직접 호출하지 않는다.

CompletableFuture 조합을 사용하며 join/get으로 Executor를 점유하지 않는다.
처리 예약부터 material.processing-timeout-minutes(기본 10분) 제한을 적용한다.
Executor 거부·서명 실패·빈 AI 응답·검증 실패·AI 예외·타임아웃은 FAILED로 처리한다.
타임아웃 이후 늦게 도착한 AI 성공 결과는 저장하지 않는다.

FILE_FETCH_FAILED는 모든 파일의 서명 URL을 다시 발급해 정확히 1회 더 호출한다.
FAILED 재시도도 material_file에서 기존 순서·객체를 읽고 전체 URL을 새로 발급한다.
오류 메시지는 코드별 안전한 안내문으로 변환하며 AI가 보낸 원문·URL·키는 그대로 저장하지 않는다.
LLM_TIMEOUT은 기존 AI_TIMEOUT, LLM_FAILED는 기존 AI_UNAVAILABLE 매핑을 사용한다.

자료 10개 제한은 `MaterialUploadedEvent(materialId,userId)`를 슬라이스 10이 커밋 후 구독하는
연동 지점만 마련했다. 자동 삭제 정책이나 상한 강제는 구현하지 않았다.
슬라이스 10은 `MaterialRepository.fileReferences(material)`로 PNG 전체 객체 참조를 먼저 확보한 뒤
Storage 객체를 정리해야 한다. material.file_url 하나만 삭제하면 나머지 이미지가 남는다.

## 검증 결과와 한계

Java 21 전체 테스트 213개와 Swagger 인증 JavaScript 테스트 10개가 모두 통과했다.
실패·오류·건너뛴 테스트는 없다.

격리 H2 PostgreSQL 모드에서 기존 슬라이스 9 listener/service/repository/writer를 그대로 사용한다.
AI-01·AI-02와 Storage만 Mock으로 대체한다.
통합 테스트에서 UPLOADED 즉시 응답 → PROCESSING → READY → 실제 이벤트 수신 →
PREPARING 조회 → 문제 40개 저장 → AVAILABLE을 확인한다.
중복 이벤트/동시 재시도, Markdown 보존, DB 롤백, 오류 종류, URL 재발급 1회도 검증한다.
별도 로컬 HTTP 서버 테스트는 Storage 업로드·서명·삭제 요청과 private 버킷/호스트/리다이렉트 검사를 검증한다.
PNG 20장 순서 보존, 21장 거절, 뒤쪽 파일 오류 시 저장 방지, 전체 URL 재발급,
실패 후 객체 재사용, 중간 업로드 실패 정리, material_file INSERT 실패 롤백도 검증한다.
V4 SQL 자체를 격리 H2 PostgreSQL 모드에서 실행해 기존 PNG 보존·순서 제약·CASCADE를 확인한다.

실제 Supabase Storage와 PostgreSQL enum/FK, 실제 AI 단원화 품질 및 Railway 배포는 미검증이다.
실행 프로세스 내 비동기 큐이므로 **프로세스 강제 종료·재시작 시 작업 유실 복구는 보장하지 않는다**.
FAILED 기록 시점에 DB까지 내려가 있으면 실패 상태 저장도 불가능하며, ID만 로그에 남으므로 운영 복구가 필요하다.
Storage 보상 삭제도 네트워크 장애 시 실패할 수 있다. durable outbox/lease와 고아 객체 정리는 후속 운영 작업이다.
이러한 복구를 위해 기존 created_at/보관 기한을 재처리 시작 시각으로 임의 변경하지 않았다.

## PNG 합의 및 남은 팀 확인 사항

- 사용자 확인으로 PNG 최대 20장, 반복 file 필드, 전송 순서, material_file 및 새 마이그레이션 계약이 확정되었다.
- V4는 이후 정상 배포/기동 시 Flyway가 적용한다. 배포 직전 다른 브랜치에 V4가 추가되지 않았는지 다시 확인해야 한다.
- 비공개 버킷·서버 키와 AI 측 SUPABASE_HOST, 서명 TTL을 확인해야 한다.
- PAST_EXAM 처리 계약과 슬라이스 10의 MaterialUploadedEvent 소비를 확인해야 한다.
- 재시작 복구용 durable 작업 상태/lease가 필요한 운영 수준도 팀과 합의해야 한다.

## Swagger 시험 순서

1. 위 환경변수를 별도로 설정하고 private 버킷을 준비한다. 우선 AI_MOCK=true AI 서버로 검증한다.
2. Swagger Google 로그인 후 과목 POST로 본인 과목을 만든다.
3. 자료 업로드 API에서 과목 ID, PDF/PPTX 한 개 또는 PNG 최대 20개, kind=LECTURE를 선택한다.
   PNG는 UI/클라이언트가 실제 전송하는 순서대로 저장된다.
4. 201 UPLOADED를 받은 뒤 상태 API를 폴링해 READY 또는 FAILED를 확인한다.
5. READY이면 DB의 material_page/category와 슬라이스 9의 문제 40개·AVAILABLE 전환을 확인한다.
6. AI 오류 Mock으로 FAILED를 만든 뒤 retry API의 202와 새 처리를 확인한다. READY 재시도는 409다.
7. 타인 계정 자료는 상태/재시도 모두 404인지 확인한다.
